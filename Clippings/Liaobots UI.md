## 第二部分：这个补正通知到底是什么

### 2.1 法律依据的准确性核对

你收到的通知引用《计算机软件著作权登记办法》第二十二条。我核对该办法条文：

《计算机软件著作权登记办法》（国家版权局令第1号，2002年2月20日发布，2002年2月20日施行）第二十二条规定："申请文件不符合本办法规定的，中国版权保护中心应当通知申请人补正，申请人应当自收到通知之日起30日内予以补正。逾期未补正的，视为撤回申请。"

结论：引用准确，30日期限属实，逾期后果属实。（置信度：高）

需要注意：逾期未补正视为"撤回申请"，不是"驳回"。 这意味着你不会留下不良记录，但登记费不退，且需要重新走全流程。这对于以软著为高企申报、科技项目验收、投标资质等用途的企业来说，时间成本可能远高于费用成本。

### 2.2 "模板化"审查的现实背景

这个问题当然不是第一次出现。事实上，2023年以来这已经成为软著审查中最高频的补正理由之一。我说明原因和背景（以下为对行业公开信息的归纳，置信度：中高）：

驱动因素一：申请量爆炸与"高企挂钩"  
软著登记量从2015年的约29万件增长到2022年的183万件量级（中国版权保护中心公开数据方向，具体数字置信度：中）。其中相当比例是为了高新技术企业认定（要求至少1项I类知识产权或5-6项II类知识产权，软著属II类）、科技型中小企业评价、政府补贴申报而"凑数"申请的。市场上存在大量"软著代办"中介，采用同一套模板批量生成材料。

驱动因素二：中心引入形式比对手段  
中国版权保护中心近年明显加强了对源代码相似度、文档结构相似度的检测。虽然中心从未公开其检测算法细节，但从大量申请人反馈的补正意见看，触发点集中在：

- 同一批次申请材料之间高度相似
- 代码大量匹配公开开源项目（GitHub、Gitee 上的知名脚手架）
- 文档使用可识别的模板骨架（尤其是网上流传的"软著说明书模板.docx"）

驱动因素三：政策收紧信号  
2021年前后，多地对以软著数量套取补贴的行为进行了清理。审查趋严是这一背景的延续。

### 2.3 网上对这个问题的典型讨论与"解法"

我梳理开发者社区（CSDN、掘金、知乎、V2EX 等）以及代办机构宣传中反复出现的应对思路，并逐条评价其有效性：

| 流传做法 | 有效性评价 | 我的判断 |
| --- | --- | --- |
| 把变量名、函数名批量改成"更个性化"的名字 | 低效且危险 | 只改标识符不改结构，形状仍然一模一样；且会破坏可编译性，若中心索要完整源码会暴露 |
| 增加注释密度，把中文注释写长 | 有一定效果但不够 | 注释确实能提升"人写"的可信度，但审查看的是代码本身的结构独特性 |
| 删掉所有 CRUD Controller，只交业务逻辑 | 有效，是正确方向 | 这是本报告的核心建议之一 |
| 把前端.vue 文件全部换成后端算法代码 | 视软件性质而定 | 你的系统确实是Web管理系统，全删前端不现实，但比例需要调整 |
| 找中介"过一遍"再交 | 高风险 | 中介的"过一遍"往往就是加噪声代码，若被识别属提交虚假材料，后果远重于补正 |
| 提交60页首尾+完整源码光盘 | 误解 | 标准做法是前30页+后30页，共60页；提交多余材料不加分 |
| 重写文档，加入大量自制截图和流程图 | 高效，正确方向 | 截图是"真实存在的软件"的最强证据 |

最重要的认知纠正： 补正不是"把材料改得看起来不像模板"，而是"证明这个软件是真实开发的、有独创性的"。前者是化妆，后者是体检。审查员见过太多化妆的了。

## 第三部分：源程序鉴别材料 —— 具体审查与修改意见

### 3.1 提交规范复核（先确保形式无误）

依据中心《计算机软件著作权登记申请办法》及公开的填表说明：

- 页数：源程序连续打印，前30页 + 后30页，共60页。若程序总量不足60页则全部提交。
- 每页行数：不少于50行（中心明确要求）
- 页眉：每页含软件全称、版本号、页码
- 内容：不得含流程图、说明性文字段落；应为可运行的实际代码

你当前材料的形式问题（我从PDF文本判断，置信度：中高）：

1. PDF 转文本后，中文与代码之间出现异常空格（如
	```
	' 巡检点编号 '
	```
	、
	```
	" 主键不能为空 "
	```
	）。这是PDF提取的伪影，但也是你原始文件的排版问题。如果是后者，需检查原始 docx/pdf 中是否存在全角空格或不当的字符间距设置。请务必核对原始提交件。
2. 文件之间以
	```

	```
	分隔——这个做法本身没问题，且有助于审查员理解项目结构，可以保留。
3. 页码连续性：从PDF看是连续的，符合要求。
4. 每页行数：从PDF密度看，部分页面代码行数偏少（尤其是Vue模板部分，因为标签换行多）。建议核对是否满足50行/页。

## 一、"文档太AI化"是一个错误的问题定位

### 1.1 审查员不认识"AI味"，也不以此为标准

这是关键认知偏差。中国版权保护中心的审查依据是《计算机软件著作权登记办法》和《计算机软件著作权登记申请办法》，其形式审查关注的是：

- 材料是否齐全、格式是否合规（页数、行数、页眉）
- 材料是否指向一个真实存在的、有独创性的软件
- 同一批次/同一申请人的材料之间是否存在异常相似

"这段话读起来像不像AI写的"从来不是审查项。 审查员没有这个训练，中心也没有这个标准。你不会因为用了"——"就被驳回。

### 1.2 真正的病因是"高度对称"，不是"文风机械"

审查员看到的是这个：

| 观察点 | 巡检系统文档 | 报警系统文档 |

## 三、修补方案：把 visual\_evidence 提升为一级证据

### 3.1 补全 schema

```json
"visual_evidence": [  {    "evidence_id": "V-001",    "kind": "ui_screenshot | architecture_diagram | flow_diagram | er_diagram | data_sample | terminal_output",    "file_path": "",    "sha256": "",    "perceptual_hash": "",    "capture_source": "live_system | test_env | design_mockup | hand_drawn | unknown",    "contains_real_data": true,    "data_state": "populated | empty_state | error_state | placeholder",    "mapped_features": ["F-001"],    "document_locations": ["6.2"],    "caption": "图 6-1 巡检点管理列表界面",    "annotations": ["①点击新增", "②填写巡检点名称"],    "privacy_scrubbed": true,    "scrub_notes": "客户名称已替换为测试数据/手机号已打码"  }]
```

### 3.2 视觉证据分级

对齐代码证据的 A/B/C/D：

| 等级 | 定义 | 举例 |
| --- | --- | --- |
| A | 真实运行环境截图，含真实业务数据，含操作标注 | 巡检点列表页有12条真实数据+红框标注操作顺序 |
| B | 真实运行环境截图，含数据但无标注 | 报警中心列表页有数据但无标注 |
| C | 真实运行截图但为空状态/占位状态 | "暂无数据"的空列表页 |
| D | 设计稿、线框图、手绘图、纯示意架构图 | Visio画的三层架构框图 |

关键规则：D级视觉证据不计入"软件真实存在"的证明。

你这次的材料里，那些架构图（如果存在）大概率是D级——它证明你会画图，不证明软件跑起来了。

### 3.3 新增硬约束

```
核心功能视觉证据覆盖率 = 有A/B级视觉证据的核心功能数 / 核心功能总数
```

阻断条件：

1. 核心功能视觉证据覆盖率 < 阈值（建议初始 80%，里程碑0影子统计后校准）→ 硬阻断
2. A/B级视觉证据总数 = 0 → 硬阻断（一张真实截图都没有的软件文档不可提交）
3. C级占比 > 40% → 警告（满篇空状态截图 = 系统没数据 = 可能没真跑起来）
4. D级被用于满足核心功能覆盖 → 硬阻断（不允许拿设计稿冒充运行截图）

豁免路径必须显式：

某些功能确实无法截图（如后端定时任务、消息推送），允许在计划中声明：

```json
{  "feature_id": "F-012",  "visual_evidence": [],  "visual_exemption": {    "reason": "后端定时调度任务无UI界面",    "alternative_evidence": ["terminal_output:V-018", "code:C-009"],    "confirmed_by_user": true  }}
```

豁免必须逐条人工确认，不允许批量豁免。 否则用户会把所有功能都标豁免。

### 3.4 新增门禁

在你的门禁矩阵里插入一行：

| 门禁 | 核心检查 | 处理方式 |
| --- | --- | --- |
| 视觉证据充分性 | 核心功能覆盖率、等级分布、真实性标记、感知哈希去重、隐私脱敏 | 覆盖率不足/零A级/D级冒充 硬阻断；C级占比过高 警告 |

对应脚本：

```
scripts/visual_evidence_check.py
```

### 3.5 感知哈希去重（防作弊）

你的测试矩阵已经想到了这一点：

> 复制同一截图并改文件名，覆盖率不能提高

实现方式：对每张图计算 perceptual hash（pHash 或 dHash），而非仅 sha256。sha256 只能防"完全相同的字节"，改一个像素就绕过。pHash 能识别"视觉上几乎相同"的图。

规则： 汉明距离 < 阈值的两张图视为同一张，只计一次覆盖。

### 3.6 空状态检测

这是一个可自动化的检测：截图中如果出现

```
暂无数据
```
、
```
No Data
```
、
```
—
```
、空表格骨架且行数为0，标记为
```
data_state: empty_state
```
，降为C级。

不需要复杂CV，OCR文本匹配 + 表格区域像素方差检测即可覆盖大部分场景。

## 五、一个方向性建议

你的方案有一个隐含假设：材料的问题都能通过检查发现。

但截图这件事的特殊性在于——它不是"发现问题"，是"逼用户去做一件麻烦事"。

补30张真实截图需要：

1. 有一个能跑起来的环境
2. 环境里有足够的测试数据
3. 逐个功能操作并截图
4. 标注、脱敏、命名、编号

这个工作量可能占整个补正工作的40%以上，而且没有任何技术手段能替代。

所以视觉证据门禁的真实作用不是"检测"，是"在用户以为完事了的时候，告诉他还差最重要的一步"。

这意味着它应该尽早触发——不是等文档生成完才检查，而是在证据计划阶段就要求用户申报每个核心功能的截图来源，让他在还没写一个字的时候就知道要去补30张图。

建议：把视觉证据的申报和确认，前置到材料证据计划的用户确认环节，与代码证据同级。计划确认时如果视觉证据覆盖不足，直接阻断进入文档生成阶段。

否则用户会：写完文档 → 门禁报"截图不足" → 发现要补30张图 → 环境早拆了 → 妥协交空文档 → 再次被驳。

## 二、核心缺陷：整套方案在证明"软件真实存在"上是空的

### 2.1 你自己写了第一性原理，然后没实现它

方案第三节第一条：

> 鉴别材料要让审查员快速确认三件事：软件真实存在、源程序能代表申请人的实际开发成果、所有材料描述的是同一个软件。

现在把这三件事和门禁矩阵对一遍：

| 第一性原理 | 对应门禁 | 覆盖情况 |
| --- | --- | --- |
| 源程序能代表实际开发成果 | 代码代表性门禁 + 来源与权属门禁 | ✅ 双门禁保障 |

## 三、必须做的调整（按优先级）

### 🔴 调整1：visual\_evidence 提升为一级公民

schema补全：

```json
"visual_evidence": [  {    "evidence_id": "V-001",    "kind": "ui_screenshot | architecture_diagram | flow_diagram | er_diagram | data_sample | terminal_output | log_output",    "file_path": "",    "sha256": "",    "perceptual_hash": "",    "capture_source": "live_system | test_env | design_mockup | hand_drawn | unknown",    "data_state": "populated | empty_state | error_state | placeholder",    "grade": "A|B|C|D",    "mapped_features": ["F-001"],    "document_locations": ["6.2"],    "caption": "",    "annotations": [],    "privacy_scrubbed": true,    "scrub_notes": ""  }]
```

分级规则：

| 等级 | 定义 |
| --- | --- |
| A | 真实运行环境 + 真实业务数据 + 操作标注 |
| B | 真实运行环境 + 有数据 + 无标注 |
| C | 真实运行环境 + 空状态/占位状态 |
| D | 设计稿 / 线框图 / 手绘 / 纯示意架构图 |

硬约束：

1. A/B级视觉证据总数 = 0 → 硬阻断
2. 核心功能视觉证据覆盖率 < 阈值 → 硬阻断
3. D级用于满足核心功能覆盖 → 硬阻断
4. C级占比 > 40% → 警告（满篇空状态 = 系统可能没真跑起来）

豁免必须逐条显式：

```json
"visual_exemption": {  "reason": "后端定时调度任务无UI界面",  "alternative_evidence": ["log_output:V-018", "code:C-009"],  "confirmed_by_user": true}
```

不允许批量豁免，否则用户会把所有功能标豁免。

新增门禁行：

| 门禁 | 核心检查 | 处理方式 |
| --- | --- | --- |
| 视觉证据充分性 | 覆盖率/等级分布/真实性/感知哈希去重/脱敏 | 覆盖率不足、零A级、D级冒充 → 硬阻断；C级占比过高 → 警告 |

去重用感知哈希而非sha256。 sha256改一个像素就绕过，pHash汉明距离能识别"视觉上几乎相同"。你的测试矩阵已经想到"复制截图改文件名不能提高覆盖率"，但实现层面必须用pHash才做得到。

空状态可自动检测： OCR匹配

```
暂无数据|No Data|—
```
\+ 表格区域像素方差检测，覆盖大部分场景，不需要复杂CV。

### 🔴 调整2：视觉证据申报必须前置到计划确认阶段

这是比调整1本身更重要的一点。

截图的特殊性在于——它不是"检测问题"，是"逼用户去做一件很麻烦的事"。

补30张真实截图需要：能跑的环境 + 足够的测试数据 + 逐功能操作截图 + 标注脱敏命名编号。

工作量可能占整个补正的40%以上，且没有任何技术手段能替代。

如果视觉证据检查放在文档生成之后，真实场景会是：

```
用户写完文档 → 门禁报"截图不足30张" → 用户发现要重搭环境造数据→ 环境早拆了/数据早删了 → 妥协交空文档 → 二次被驳
```

必须改成：

```
业务分析 → 生成证据计划（含视觉证据申报清单）→ 用户确认时看到"你需要补拍32张截图，清单如下"→ 视觉证据覆盖不足 → 阻断进入文档生成阶段
```

让用户在还没写一个字的时候就知道要去补32张图。

这一条改动的价值大于门禁本身。

### 🟡 调整5：署名处理需要三分法，现在写得太粗

方案的二阶风险表写：

> 修改框架署名制造虚假权属 → 明确禁止修改来源信息

这条如果照字面实现，会误伤。必须拆成三种情况：

| 情况 | 正确处理 |
| --- | --- |
| 文件确实是框架生成/第三方代码 | 不改署名，直接移出材料 |
| 文件是自己写的，但用了带默认署名的生成器骨架 | 改为真实作者，且需记录改动依据 |
| 无法判断归属 | 标 ``` source_kind: unknown ``` → 移出材料 |

否则实现者会理解成"一律不许改"，导致自己写的代码因为顶部有生成器留的署名而被误排除。

## 一、目标定义

## 二、失败链路与本次反馈的直接根因

### 2.1 失败链路

```
规划阶段选入大量低价值模板代码→ 文档生成阶段复用固定章节、表格和句式→ 文档缺乏真实运行证据，审查员无法确认软件存在→ 门禁只检查格式，未检查代表性、真实性、结构模板化和逻辑一致性→ 用户看到"已生成"，误以为已经可提交→ 审查员识别出模板化和自相矛盾，或无法确认软件真实性
```

### 2.2 本次反馈直接暴露的六类根因

| # | 根因 | 严重度 |
| --- | --- | --- |
| 1 | 源程序混入大量低价值模板代码（CRUD 六件套、同构 API 封装、实体/DTO、配置） | 高 |
| 2 | 源程序残留第三方作者署名，存在权属瑕疵 | 最高 |
| 3 | 文档缺乏真实界面截图，无法证明软件真实存在 | 高 |
| 4 | 文档过度形式化（功能清单表格模板、重复的"异常功能逻辑"小节、固定章节骨架） | 高 |
| 5 | 门禁未检查文档前后内容一致性（6 种策略只列 4 条、步骤编号从 4 开始、章节跳号） | 中高 |
| 6 | 门禁未检查文档逻辑性（X 轴与 Z 轴取值相同、操作路径与内容不符） | 中高 |
| 7 | 标点符号习惯高度统一（AI 文风弱信号，非主因） | 低 |

> v0.3 新增说明： 根因 3 在 v0.2 中缺失。它是"软件真实存在"这一第一性原理的直接对应项，且是最难自动生成、最能证明真实性的证据类型。

## 三、第一性原理

1. 鉴别材料要让审查员快速确认三件事：
	- ① 软件真实存在
		- ② 源程序能代表申请人的实际开发成果
		- ③ 所有材料描述的是同一个软件
2. 真实性优先于文风。 任何功能、规则、作者、日期、截图和路径都必须有真实来源。
3. 代表性优先于复杂度。 简单软件可以用领域约束、交互流程和真实使用过程证明代表性。
4. 有限篇幅用于最大化证据信息量。 页数是排版约束，不是凑满目标。
5. 门禁必须可解释、可失效。 任何上游变化都必须让下游确认自动过期。
6. 人工确认必须有实际内容，不能只点"已确认"。
7. 【v0.3 新增】最难自动化的证据，往往是最有价值的证据。 系统不得因某类证据难以算法处理而将其降级或忽略。

### 3.1 三条原理与门禁的对应关系（必须全覆盖）

| 第一性原理 | 主门禁 | 辅助门禁 |
| --- | --- | --- |
| ① 软件真实存在 | 视觉证据充分性门禁 | 文档证据门禁 |
| ② 源程序代表实际成果 | 代码代表性门禁 | 来源与权属门禁 |
| ③ 材料描述同一软件 | 逻辑一致性门禁 | 跨材料一致性门禁 |

> 设计约束： 三条原理必须各有至少一道硬阻断门禁。任何一条裸奔即视为方案不完整。

## 四、首个可用版本的最小闭环

### 4.1 主流程

```
业务与项目分析→ 生成材料证据计划（含事实断言表 + 视觉证据申报清单）→ 【用户确认计划】← 视觉证据不足在此阻断，不进入下游→ 抽取源程序并检查最终选材与连续性→ 按计划生成技术初稿→ human-writing 受限改稿 + 事实回归→ 单文档逻辑一致性门禁→ 视觉证据充分性门禁→ 同批次结构模板化门禁→ 用户确认 Markdown→ 生成 DOCX/PDF→ 最终提交件复检
```

### 4.2 九个必做项，缺一不可

1. 关闭固定章节、表格、FAQ 和篇幅激励。
2. 建立证据计划与人工确认。
3. 【v0.3 新增】视觉证据申报前置到计划确认阶段。
4. 检查最终源码选材，而非候选池。
5. 【v0.3 新增】检查视觉证据充分性与真实性。
6. 检查单文档逻辑一致性。
7. 检查同批文档结构模板化。
8. 接入受限 human-writing 和事实回归。
9. 复检最终 DOCX/PDF 提交件。
10. 生成与审查解耦，独立检查上下文。

### 5.3 事实断言表

事实断言表是逻辑一致性门禁的核心输入，必须随计划一起生成和确认。

| 类型 | 含义 | 检查用途 |
| --- | --- | --- |
| ``` count ``` | 数量断言，如策略总数、状态总数 | 检查表格行数、列表项数与正文数字是否一致 |
| ``` range ``` | 取值断言，如 XYZ 维度取值集合 | 检查集合是否重复或冲突 |
| ``` enum ``` | 枚举断言，如状态集合、角色集合 | 检查引用是否越界 |
| ``` transition ``` | 状态流转断言 | 检查前后文是否矛盾 |
| ``` mapping ``` | 映射断言，如功能/页面/操作路径/字段的对应关系 | 检查双向一致性 |

source 取值说明（v0.3 扩展）：

| source | 含义 | 典型场景 |
| --- | --- | --- |
| ``` business_context ``` | 来自业务理解 | 用户描述的业务规则 |
| ``` code ``` | 来自源代码 | 枚举类、常量定义、状态机 |
| ``` visual ``` | 来自截图 | 下拉框选项数、列表列数、状态标签种类 |
| ``` user_confirmed ``` | 用户显式确认 | 无法从代码推断的业务约定 |
| ``` cross_document ``` | 跨材料引用 | 软件名称、版本号、开发完成日期 |

> ```
> visual
> ```
> 的价值： 支持图文交叉校验。文档写"任务状态共 5 种"，截图里下拉框只有 4 项 → 矛盾。这比纯文本内部一致性检查更接近真实性验证，且自动化可行（OCR + 计数）。

每条断言必须带

```
source
```
和
```
source_ref
```
。没有来源的断言不允许进入计划。

### 5.4 代码证据分级

| 等级 | 定义 |
| --- | --- |
| A | 核心算法、状态机、策略/责任链、调度、复杂查询、项目专属数据转换 |
| B | 真实业务流程、自定义校验、跨模块处理、项目专属交互逻辑 |
| C | 具有少量业务语义的普通服务、页面或控制层 |
| D | 纯 CRUD、纯 API 封装、实体/DTO、配置、路由、生成器骨架、第三方代码 |

固定硬约束：

- 每个核心功能至少有一项可追溯的 A/B 级证据
- 权属、来源或许可证存在未解决冲突时阻断
- 完全没有 A/B 级证据时阻断
- 不能通过修改源码、署名或注释来迎合门禁

### 5.5 【v0.3 新增】视觉证据分级

| 等级 | 定义 | 判定要点 |
| --- | --- | --- |
| A | 真实运行环境截图 + 真实业务数据 + 操作标注 | 列表有多行真实数据、含红框/序号标注 |
| B | 真实运行环境截图 + 有数据 + 无标注 | 列表有数据但无操作引导 |
| C | 真实运行环境截图 + 空状态/占位状态 | "暂无数据"、空表格骨架、全部字段为 ``` — ``` |
| D | 设计稿 / 线框图 / 手绘图 / 纯示意架构图 | Visio 框图、Figma 原型、PPT 示意图 |

核心规则：D 级视觉证据不计入"软件真实存在"的证明。

它证明设计能力，不证明软件跑起来了。

硬约束：

| # | 条件 | 处理 |
| --- | --- | --- |
| 1 | A/B 级视觉证据总数 = 0 | 硬阻断 |
| 2 | 核心功能视觉证据覆盖率 < 阈值（初始 80%，里程碑 0 校准） | 硬阻断 |
| 3 | D 级被用于满足核心功能覆盖要求 | 硬阻断 |
| 4 | 存在 ``` capture_source: unknown ``` 的证据被计入覆盖 | 硬阻断 |
| 5 | C 级占比 > 40% | 警告（满篇空状态 = 系统可能未真实运行） |
| 6 | 提交版存在 ``` privacy_scrubbed: false ``` 的截图 | 硬阻断 |

豁免路径（必须逐条显式）：

```json
"visual_exemption": {  "reason": "后端定时调度任务无 UI 界面",  "alternative_evidence": ["log_output:V-018", "code:C-009"],  "confirmed_by_user": true,  "confirmed_at": "2026-08-29T10:00:00Z"}
```

- 不允许批量豁免。 每条豁免必须单独确认，且必须提供替代证据。
- 豁免率是一级观测指标。 豁免率飙升 = 用户在绕过机制。

去重规则：

- 使用 perceptual hash（pHash/dHash） 而非仅 sha256
- sha256 只能防"完全相同的字节"，改一个像素即绕过
- 汉明距离 < 阈值的两张图视为同一张，只计一次覆盖

空状态自动检测（可实现路径）：

- OCR 文本匹配：
	```
	暂无数据|无数据|No Data|Empty|—|--
	```
- 表格区域像素方差检测：方差低于阈值判定为空表骨架
- 命中任一条件 → 强制标记
	```
	data_state: empty_state
	```
	→ 降为 C 级

### 5.6 源码连续性规则

不允许任意行段碎片化抽取：

- 只允许抽取完整文件，或完整函数、完整类的连续区间
- 抽取时必须保留函数签名、类声明和必要上下文，保证可读
- 保存原始路径、原始行号、哈希和编排顺序，生成源码材料序列清单
- 最终材料从序列清单确定分页，生成后不得跳行拼接
- 对最终选中的代码总量重新统计低价值占比，而非只评价候选文件

比例类规则先影子统计，再根据回归样本确定阈值：

- 核心功能证据覆盖率必须为 100%
- 权属不明代码为 0
- 纯模板代码不能成为材料最大组成部分
- 低价值占比超过校准阈值时阻断，其余为警告

### 5.7 【v0.3 新增】署名与权属处理三分法

v0.2 的"明确禁止修改来源信息"如果照字面实现会误伤自研代码。必须区分三种情况：

| 情况 | 判定依据 | 正确处理 |
| --- | --- | --- |
| 确为第三方/框架生成代码 | 文件整体结构匹配已知框架模板；作者标签为已知开源项目作者 | 不改署名，直接移出材料（ ``` resolution: exclude ``` ） |
| 自研代码但使用了带默认署名的生成器骨架 | 文件含大量项目专属业务逻辑；作者标签为生成器默认值 | 改为真实作者，并记录 ``` resolution_basis ``` （ ``` resolution: replace ``` ） |
| 无法判断归属 | 无法确认来源 | 标 ``` source_kind: unknown ``` → （ ``` resolution: exclude ``` ） |

对情况一的文件执行

```
replace
```
。此为伪造权属，系统必须拒绝。

已知框架作者标签库： 系统应维护一个可扩展的常见开源框架作者标签清单（如 RuoYi 系列、若干脚手架的默认署名），命中即触发情况一判定并要求人工复核。

### 6.2 结构模板化与文风风险分离

结构模板化门禁（强信号）：

- 同批文档目录树高度相同
- 功能清单表格列结构完全一致
- 重复的"异常功能逻辑"类小节
- 章节篇幅、表格数量和排列方式高度对称
- 大量段落只是替换模块名称

同批文档需提交

```
submission_batch_id
```
，检查器对批次内文档。相似内容如果来自真实共享平台，可通过边界声明说明，但不能靠随机调整标题逃避检测。

文风风险门禁（弱信号）：

- 标点习惯高度统一
- 固定路标和模型惯用黑话
- 同构句式和段落形状

默认进入修订循环或警告，不单独阻断提交。

### 6.3 逻辑一致性门禁

输入事实断言表，输出每个断言的验证结果：

| 断言类型 | 检查内容 |
| --- | --- |
| 数量断言 | 正文数字与表格行数、列表项数是否一致 |
| 编号断言 | 章节、步骤、表格序号是否连续、从 1 开始、无跳号 |
| 枚举断言 | 状态、角色、维度取值是否与定义一致，不同维度取值集合是否重叠 |
| 状态流转断言 | 前后文描述的状态变化是否合法 |
| 映射断言 | 功能、页面、操作路径、字段引用是否双向一致 |
| 【新增】图文交叉断言 | 截图内可识别的枚举项数量 / 列数 / 状态标签种类，与文档描述是否一致 |

明确矛盾硬阻断。无法自动判定的语义问题进入人工复核，不允许静默放行。

### 6.4 【v0.3 强化】申请独立性门禁

v0.2 只防"真实相似被误杀"，未防"实质同一被拆分申请"。后者是真实合规风险。

计算：

```
功能边界重叠度 = |A.included_boundaries ∩ B.included_boundaries| / min(|A|, |B|)共享代码占比   = 共享文件数 / 各自材料总文件数
```

处理：

| 条件 | 处理 |
| --- | --- |
| 两项指标均超阈值 | 警告 + 强制填写独立性声明，不硬阻断 |
| 用户未填写 ``` independence_declaration ``` | 阻断进入下游 |

提示文案：

> 检测到本批次两份材料共享 X% 代码基础，功能边界重叠 Y%。  
> 请确认这两个软件在功能上可独立运行、可分别交付。  
> 若实为同一软件的两个模块，建议合并为一份申请。  
> 说明：登记机关对"同一软件不得重复登记"有明确态度。

不宜硬阻断（会误伤真实模块化产品），但必须显式提示并要求逐项确认。

### 6.5 跨批次结构比较

同批次任务共享

```
submission_batch_id
```
，检查：

- 目录树相似度
- 表格结构指纹
- 重复小节名称和重复段落
- 截图和模块重合（含 pHash 比对）
- 共享平台代码与各自独有代码的边界

### 6.6 最终提交件复检

Markdown 检查通过不等于提交件正确。最终流程必须是：

```
Markdown 检查→ 生成 DOCX/PDF→ 重新提取最终文件文本和结构→ 再检查编号、表格、图片、页眉、逻辑事实和证据映射→ 校验图片是否完整嵌入（不是断链、不是白框）→ 生成最终文件哈希
```

用户手工编辑最终文件后，原"可提交"状态自动失效，必须重新检查。

### 6.7 生成与审查解耦

- 确定性规则由脚本执行
- 逻辑审查使用独立检查上下文，不读取生成过程中的自我解释
- 检查器只读取最终材料、事实断言表和证据映射
- 每个问题必须给出冲突位置、引用文本和依据
- 最多自动修订两轮，仍未通过则交给人工

## 七、【v0.3 新增】视觉证据前置机制

### 7.1 为什么必须前置

截图的特殊性：它不是"检测问题"，是"逼用户去做一件麻烦事"。

补 30 张真实截图需要：

1. 有一个能跑起来的环境
2. 环境里有足够的测试数据
3. 逐个功能操作并截图
4. 标注、脱敏、命名、编号

这个工作量可能占整个补正工作的 40% 以上，且没有任何技术手段能替代。

### 7.2 如果不前置会发生什么

```
用户写完文档→ 门禁报"截图不足 30 张"→ 用户发现要重搭环境造数据→ 环境早拆了 / 数据早删了→ 妥协交空文档→ 二次被驳
```

### 7.3 正确的前置流程

```
业务分析→ 生成证据计划，自动产出「视觉证据申报清单」→ 用户确认时看到：「你需要补拍 32 张截图，清单如下」→ acquisition_status 全部为 pending 时阻断→ 用户逐张标记 acquired / exempted→ 覆盖率达标后才允许进入文档生成阶段
```

### 7.4 视觉证据申报清单示例（供用户确认时展示）

```
【视觉证据申报清单】共 32 项，当前状态：0 已获取 / 32 待补拍
核心功能（必须提供 A/B 级证据）：[ ] V-001  巡检点管理-列表页        F-001  建议含 10+ 条真实数据[ ] V-002  巡检点管理-新增表单      F-001  建议含操作标注①②③[ ] V-003  巡检点管理-检查项配置    F-002  建议展开四级结构[ ] V-004  巡检计划-推送策略配置    F-005  建议展示 6 种策略下拉...
可豁免项（需填写理由与替代证据）：[ ] V-030  定时任务调度            F-012  无 UI → 建议提供日志截图
```

## 八、human-writing 集成

### 8.1 正确定位

- 在事实初稿完成后，降低固定句式、机械路标、同构排比和模型黑话
- 运行
	```
	check_prose.py
	```
	，输出"模型化文风风险"
- 不得输出"AI 检测结果"或"非 AI 创作证明"

### 8.2 技术文档受限模式

只处理普通叙述段落。以下内容全部锁定：

- 软件名称、版本、模块、菜单、按钮、角色、状态和字段
- 数字、日期、步骤、策略数量和图号
- 表格、代码块、路径、网址和机器字段
- 申请表字段、法定信息和截图引用与图注

原始"禁冒号、禁破折号"规则不直接套用整份技术文档。标题、表格、字段和图注先屏蔽。

### 8.3 改写后事实回归

- 确定性检查： 锁定名称、数字、状态、路径、图号和引用必须完全一致
- 语义检查： 新增、删除或改变功能含义时进入人工复核
- 事实漂移立即回退并硬阻断

### 8.4 依赖治理

- 记录 human-writing 版本、规则摘要和脚本哈希
- 支持
	```
	off | advisory | required
	```
	三种模式
- 依赖缺失或版本不兼容时必须形成明确报告，不得静默跳过

## 十一、测试矩阵

### 11.1 代码证据

1. 高度重复 CRUD、API、实体和配置组成的材料被识别
2. 责任链、状态机、复杂查询、归并和矩阵转换被识别为强证据
3. 只有简单业务逻辑但具有真实领域约束的软件能够通过
4. 给源码增加注释、业务词或死代码不能提高代表性等级
5. 行段抽取必须保持完整函数、连续区间和原始行号

### 11.2 【v0.3 新增】视觉证据

1. 零截图文档被硬阻断
2. 仅有设计稿/线框图（全 D 级）的文档被硬阻断
3. 全部为空状态截图（全 C 级）触发警告并超阈值时阻断
4. 复制同一截图改文件名，覆盖率不能提高（pHash 去重）
5. 轻微修改截图像素（加水印、改亮度），仍被识别为重复
6. 截图申报清单在计划确认阶段可见，全部 pending 时阻断
7. 豁免必须逐条确认，批量豁免被拒绝
8. 未脱敏截图（含手机号/客户名/密钥）在提交版被硬阻断
9. ```
	capture_source: unknown
	```
	的证据不计入覆盖
10. 图文交叉校验：文档写"5 种状态"、截图仅 4 项 → 矛盾被发现

### 11.3 权属与署名

1. 框架生成文件（情况一）执行 replace 被系统拒绝
2. 自研文件含生成器默认署名（情况二）允许 replace 并要求填写依据
3. 无法判断归属（情况三）自动移出材料
4. 已知框架作者标签命中时触发人工复核

### 11.4 文档与逻辑

1. 自然文风但内容空泛的文档仍被证据门禁阻断
2. 模型化文风但事实充分的文档只进入文风修订
3. 本次补正中的编号跳跃、策略数量冲突和维度矛盾可回归复现
4. 同批两份文档目录、表格和小节同构时触发阻断
5. 功能边界重叠度超阈值时强制填写独立性声明

### 11.5 流程与绕过

1. human-writing 改变名称、数字、按钮、状态或图号时硬阻断
2. 计划确认后修改代码或文档会使下游状态失效
3. 缺少 human-writing、版本不兼容和脚本失败均有明确处理
4. 旧任务不迁移时保持原输出
5. 直接调用构建脚本不能绕过最终门禁
6. DOCX 生成后重新提取文本仍能通过复检
7. DOCX 生成后图片断链/白框被发现
8. 人工编辑最终文件后原状态自动失效

### 11.6 变形测试

1. 只增加注释，结论不能从失败变通过
2. 只调整标点，独创性结论不能改变
3. 调换章节顺序，事实一致性结论不能改变
4. 复制同一截图并改文件名，覆盖率不能提高
5. 把设计稿改名为"运行截图"，等级不能从 D 变 A

## 十二、观测指标

### 12.1 主要指标

证据完整性：

- 核心功能代码证据覆盖率
- 核心功能视觉证据覆盖率
- A/B 级视觉证据占比
- 视觉证据豁免率（豁免率飙升 = 用户在绕过机制，最重要的反作弊指标）
- 无来源事实数量（目标为零）

质量与拦截：

- 文风改写后的锁定事实变化数（目标为零）
- 陈旧确认被捕获次数
- 结构模板化阻断次数和误报率
- 视觉证据门禁阻断次数和误报率
- 逻辑一致性发现的问题数及人工复核占比

最终效果：

- 按软件类型统计的补正率和二次补正率

成本：

- 扫描耗时、缓存命中率和外发数据量
- 图像处理耗时（pHash + OCR）

### 12.2 禁止作为主要指标

- 门禁通过率
- 文档字数
- 表格数量
- 截图总数（覆盖率可以，总数不行）
- 代码复杂度总分
- "AI 概率"

## 十三、完成定义

1. 新任务必须有经确认的材料证据计划
2. 核心功能全部具备代码、文档和视觉证据映射；无法提供视觉证据时有真实、明确的豁免原因和替代证据
3. 视觉证据申报在计划确认阶段完成，不允许延后到文档生成之后
4. 权属、来源、事实漂移、明确矛盾、结构模板化、视觉证据不足和陈旧确认能够硬阻断
5. 署名处理遵循三分法，禁止对第三方代码执行署名替换
6. 文档不再受固定章节、表格、FAQ 和样本篇幅驱动
7. human-writing 仅作用于叙述正文，并经过事实回归
8. 同批次文档经过结构模板化比较和申请独立性检查
9. 最终 DOCX/PDF 提交件经过复检，含图片完整性校验
10. 所有新门禁有单元测试、集成测试和匿名回归样本
11. 每期都可以独立关闭或回滚
12. 输出明确声明"降低补正风险，不保证登记机关最终结论"

你这四条里，第 2 条是全案最有价值的批评。

我在设计视觉证据体系时，把"真实性"当成了可检测属性——写了

```
capture_source
```
字段、写了 A/B/C/D 分级、写了测试 37，整套看起来很完备。但它建立在一个错误前提上：机器能分辨真实截图和设计稿。

分辨不了。

正确的做法不是假装能检测，而是明确划出机器能做的和不能做的边界，把不能做的部分诚实地标注为"用户声明，未经验证"。这样至少责任归属清晰，且用户知道哪些地方需要自己把关。

一个诚实标注能力边界的系统，比一个假装全知的系统更可信，也更安全——因为后者会让用户误以为"系统说通过就没问题"，而这恰恰是我在方案第一章明确要避免的东西。
