# 规则场景推演

推演日期：2026-09-25

最近复核：2026-09-25（双核心 Skill 实施审查修正后）

本文件使用当前 `规则/` 检查协作路径是否闭合。它是验证证据，不是第二套规则。对象含义以 `规则/内容对象.md` 为准，动作顺序以 `规则/协作协议.md` 为准。

## 结论摘要

| 场景 | 纸面结果 | 主要证据 |
|---|---|---|
| 1. 快速保护闪念 | 闭合 | 捕捉协议与“只记录”硬边界 |
| 2. 带链接讨论并形成闪念 | 闭合 | 捕捉、统一来源登记、正式闪念入口 |
| 3. 辨析后放弃 | 闭合 | `dismissed` 的历史与召回后果 |
| 4. 进入发酵 | 闭合 | 单段自然语言备注，不强制问卷 |
| 5. 形成永久认识 | 闭合 | 用户认领、版本历史和真实形成依据 |
| 6. 召回历史上下文 | 闭合，待真实评估相关性 | 结构化过滤与失败降级 |
| 7. 同一来源多次出现 | 语义闭合，去重实现待后置 | 来源身份唯一、追加引用和快照 |
| 8. 内部依据不是外部来源 | 闭合 | 形成依据与外部来源身份分离 |
| 9. 成熟判断直接形成认识 | 闭合 | 不强制闪念和保鲜窗口 |

“闭合”只表示规则能够给出一致行动，不表示交互已经通过真实使用验证。

## 场景 1：只想快速保护闪念

输入：用户说“我突然想到一件事，先帮我记下来”，表达后又说“只记录”。

推演：

1. Agent 识别明确捕捉意图，创建 Markdown 原始思考会话并先保存触发消息。
2. Agent 正常回应当前表达，不询问分类、去向或格式字段。
3. 后续双方可见消息原样追加；即使表达出现分支，也不在现场中实时拆分会话。
4. 用户说“只记录”后，Agent 只确认记录完成并关闭窗口。
5. 不生成候选，不创建正式闪念；会话仍可按 ID 找回。

可撤回点：用户可以在关闭前纠正对话内容；关闭不会制造任何认识结论。

结果：闭合。“只记录”不会被结束时的候选询问绕过。

## 场景 2：带文章链接讨论并形成闪念

输入：用户发送带跟踪参数的文章链接，表达由文章触发的想法，并明确要求记录这段思考。

推演：

1. 捕捉协议先保存整条用户消息，链接处理不抢占表达。
2. 原始链接和出现位置提交统一来源登记。
3. 如果能确定规范身份，复用或建立来源；不能确定时保留 `pending_identity`。
4. 内容获取在后台进行，失败只更新来源记录，不终止对话。
5. 到达自然结束点后，如果用户主动要求或确有清晰认知种子，Agent 才询问是否整理候选；候选必须可见，用户可修改、拆分或拒绝。
6. 用户认领后才创建正式闪念，并记录会话及实际来源快照作为形成上下文。
7. 当前可调保鲜窗口从认领时刻开始，来源抓取时间不影响它。

失败分支：文章无法获取时，闪念仍可基于用户表达成立；来源标记失败，不编造文章正文。

未进入分支：如果用户只是分享链接和感想但没有表达记录意图，Agent 不创建会话或文件；在自然停顿处最多建议捕捉一次。用户确认后才创建会话，并只把确认明确涵盖的前序可见消息作为带入上下文保存。

结果：闭合。真实试运行需要观察来源处理是否仍会在交互上打断用户。

## 场景 3：辨析后放弃

输入：用户回看闪念，认为它只是短暂兴奋。

推演：

1. Agent 展示闪念和必要形成上下文，不要求用户先完成论证。
2. 用户决定放弃后，将状态记录为 `dismissed`。
3. 原内容和状态历史保留；会话、来源及其身份不受影响。
4. 该闪念退出待辨析和默认召回，但可以在历史查询中找到。

结果：闭合。系统不会用“转化率”压力阻止零产出。

## 场景 4：进入发酵

输入：用户认为闪念可能有价值，但目前缺少实际经验。

推演：

1. Agent 只澄清当前决定所需内容，不依次追问固定字段。
2. 用户决定保留后，状态转为 `fermenting`。
3. 记录一段自然语言备注，例如“可能有价值，但我还没有实际经验；下次项目复盘时再看”。
4. 以后仅在高度相关时谨慎召回，并明确显示“尚未完成”，不能当作当前确定判断。

结果：闭合。备注可以同时表达原因、缺口或重启条件，也可以只表达当下真实存在的部分。

## 场景 5：形成永久认识

输入：用户在辨析和讨论后形成一项阶段性判断。

推演：

1. Agent 只补充独立理解所必需的理由或边界。
2. Agent 展示完整候选和实际形成依据。
3. 用户可以修改、拆分或拒绝；只有明确认领后才创建永久认识。
4. 新认识状态为 `active`，当前内容成为 v1。
5. 参与形成的闪念转为 `formed`，但其原文和历史继续保留。
6. 后续修订追加 v2、v3，不产生 `revised` 生命周期状态；用户停用时才转为 `retired`。

结果：闭合。认识的当前版本与历史版本可以同时追溯。

## 场景 6：召回历史上下文

输入：用户提出一个与过去讨论相关的问题。

推演：

1. 先按身份、状态、时间和显式形成依据筛选。
2. 默认优先少量 `active` 永久认识。
3. 只有确实影响当前判断时才带入 `fermenting` 闪念，并显示未完成身份。
4. `dismissed`、`expired` 和 `retired` 默认不出现；原始会话只作为历史现场。
5. Agent 说明每条内容为什么相关，不把外部来源表述成用户观点。
6. 没有结果或检索失败时，直接继续当前讨论。

结果：语义闭合。相关性、噪声和节省重复解释的程度只能通过真实试运行判断。

## 场景 7：同一来源从多个场景出现

输入：用户先在捕捉中发送带跟踪参数的链接，后来单独保存规范链接。

推演：

1. 两次输入都进入统一来源登记，不存在“捕捉来源”和“资料来源”两个入口。
2. 身份解析将两个引用判断为同一逻辑内容时，第二次复用已有来源 ID。
3. 第一次记录会话使用关系；第二次增加原始引用或使用记录。
4. 如果重新获取了内容，在同一来源下追加快照，不创建第二个来源。
5. 如果身份解析无法可靠确认，先保留待识别记录，不能猜测合并或猜测新建。

结果：规则语义闭合。稳定规范化、并发幂等和原子写入属于未来可能需要的确定性能力，必须由真实使用量证明后再实现。

## 场景 8：内部形成依据不是外部来源

输入：用户根据一条旧闪念和一次新原始思考形成认识，没有使用网页或文件。

推演：

1. 候选列出旧闪念和新会话作为形成依据。
2. 用户认领后创建永久认识。
3. 不调用来源登记，不为会话或闪念伪造来源对象。
4. 认识的外部来源列表保持为空。
5. 以后真正补充外部材料时，该材料再经统一入口登记并建立新的形成或使用记录。

结果：闭合。形成依据是一种可追溯关系，不是“来源对象”的别名。

## 场景 9：成熟判断直接形成永久认识

输入：用户已经清楚表达一项阶段性判断，并明确要求形成永久认识。

推演：

1. 不先制造闪念，也不等待保鲜窗口。
2. Agent 只澄清独立理解真正缺少的必要理由或边界。
3. Agent 展示完整候选和真实形成依据，通常至少包含当前原始会话。
4. 用户认领后创建 `active` 永久认识 v1。
5. 如果用户拒绝候选，只保留原始会话，不产生正式认识。

结果：闭合。闪念是一条合法路径，不是永久认识的强制前置状态。

## 补充边界场景

| 边界 | 推演结果 |
|---|---|
| 捕捉后零产出 | 关闭会话即可，不制造候选或正式对象 |
| 一次会话出现多个种子 | 分别展示候选，由用户独立认领、合并或放弃 |
| 候选被拒绝 | 候选可以丢弃，原始会话不受影响 |
| 来源获取失败 | 保留引用和失败事实，当前对话继续 |
| 召回失败 | 明确未找到或失败，当前对话继续 |
| 保鲜期限到达时仍在讨论 | 不在对话中途失效，结束后再记录去向 |
| 发酵后重新激活 | 用户决定转回 `pending`，使用当时配置开始新窗口 |
| 认识被修订 | 追加用户认领的新版本，状态仍为 `active` |
| 认识被停用 | 状态转为 `retired`，所有版本和形成依据保留 |
| 只有概念、作者或书名 | 没有实际材料，不创建外部来源 |

## 需要真实使用回答的问题

1. 用户会用哪些自然语言稳定表达“开始捕捉”和“只记录”？
2. 48 小时是否过短、过长，还是需要按场景调整？
3. Agent 在什么情况下询问候选最不打断用户？
4. 一段发酵备注是否足够支持未来重新进入？
5. 多少召回内容既能减少重复解释，又不会改变当前思路？
6. Markdown 元数据在手工使用中是否产生明显负担？
7. 来源身份重复在真实数据中出现多频繁，是否足以支持开发确定性去重？

这些问题不得通过继续扩写规则或提前写 Kernel 来假装已经回答。
