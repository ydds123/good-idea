# 工作协议

本文件定义协作顺序。对象含义和状态后果以 `objects.md` 为准。

## 捕捉协议

进入条件：用户明确表示要记录、捕捉、保存当前想法，或明确续接已有思考现场。普通聊天不会被静默转成捕捉会话。

1. 立即建立或续接原始思考会话，先保存触发消息。
2. Agent 直接回应用户正在思考的内容；后续全部可见消息按顺序保存。
3. 链接、文件、来源处理和历史召回只作为上下文，不抢占前台表达。
4. 只有答案会实质改变理解或下一步时才提问，一次最多推进一个关键问题。
5. 用户说“只记录”时，确认已经记录并关闭本次窗口；不再提问、不生成候选、不建议下一步。
6. 在自然结束点，Agent 可以询问是否需要整理闪念候选；未经用户认领，不产生正式闪念。
7. 一次会话可以零产出，也可以形成多个彼此独立的候选。

## 闪念辨析协议

目标是判断这条闪念是否值得继续占用注意力，而不是把它包装成完整文章。

1. 先呈现闪念原文、认领时间和必要形成上下文。
2. 只讨论会改变价值判断的异常、连接、缺口或反例。
3. Agent 可以指出可能价值和重复，但不能替用户决定去向。
4. 合法结果包括放弃、进入发酵、形成认识，或者暂时无结论。
5. 进入发酵时记录一段自然语言备注，不用固定问卷补齐用户未表达的内容。
6. 活跃讨论不会因为计时到点而中断或失效；讨论结束后再记录去向。
7. 用户没有作出决定时保持原状态；达到保鲜期限且没有活跃讨论，才按默认规则转为失效。

## 认识完善协议

可以从一条或多条正式闪念进入，也可以由用户已经成熟的判断直接进入，不强制经过闪念或等待保鲜窗口。

1. 明确用户当前真正想成立的判断。
2. 只追问独立理解所缺少的必要理由，以及确实影响适用范围的边界、反例或不确定性。
3. 展示一份完整候选，清楚区分 Agent 的整理与用户原话。
4. 同时列出真实形成依据，不为了显得完整而制造来源或关系。
5. 用户可以认领、修改、拆分、合并或拒绝候选。
6. 只有用户认领后才正式创建新认识或新修订版本。
7. 一次讨论允许形成零项、一项或多项永久认识。

## 上下文召回协议

只有历史内容可能实质减少重复解释、暴露冲突或改善当前判断时才召回。

1. 先按对象身份、生命周期状态、时间和显式形成依据过滤。
2. 再检索标题和正文；基础检索被真实使用反复证明不足后，才考虑语义候选。
3. Agent 只选择少量真正影响当前讨论的内容，并说明为什么相关。
4. 默认优先 `active` 永久认识。
5. `fermenting` 闪念必须标明尚未完成；`pending` 只在辨析或用户明确要求时出现；`dismissed`、`expired` 和 `retired` 默认排除。
6. 原始会话只是历史现场，外部来源只是材料，二者都不代表用户当前立场。
7. 没有相关内容时明确说没有找到；检索失败时继续当前对话，不要求用户等待或重新表达。

## 统一来源登记协议

适用范围：网页、文件、书籍章节、外部文本及其他实际存在的外部材料。只提到一个概念、作者或书名，不足以创建来源。

1. 先在当前会话中保存用户的原始引用和表达。
2. 登记输入只包含原始引用、材料类型、带入者、出现上下文和持久化意图。
3. 解析规范身份，并在新旧来源中查询是否已经存在。
4. 找到既有身份时，增加原始引用、使用记录或快照版本，不创建第二个来源。
5. 身份确定且不存在时，创建 `pending_fetch` 来源；身份不确定时，只保存 `pending_identity` 记录，不猜测性创建正式身份。
6. 内容获取只为已有来源身份增加快照，并记录完整、部分或失败结果。
7. 获取失败不影响当前讨论，也不撤销已保存的原始引用。
8. 用户当前表达、原始会话、闪念和永久认识永远不经过来源登记。

用户主动带入材料用于当前捕捉时，允许登记为本轮上下文；其他场景需要明确保存意图。Agent 另行发现的材料只有在用户同意持久化后才能登记。

## 规则演化协议

1. 在真实使用记录中写下具体场景、预期、实际结果和摩擦。
2. 判断问题属于单次异常、启发式、可调默认、工作协议还是硬边界。
3. 优先调整启发式或默认值，并继续试运行。
4. 同类问题反复出现后，才修改协议。
5. 只有涉及作者权、内容身份、单一入口或历史保护时，才修改系统宪法。
6. 规则修改后，在 `decisions.md` 记录原因和生效日期，并更新相关场景推演。
