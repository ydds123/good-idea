# Good idea v0.1 决策冻结

冻结日期：2026-08-04

1. 从概念出发独立实现，不复用或迁移 `my-wiki`、`llm-wiki` 的代码、结构、数据和工作流。
2. 完整保留闪念、溯源、有意思、待办、永久五个空间；永久空间保留永久、母题、行动、索引四类卡片。
3. [已由第 19 项覆盖] 溯源空间没有两个子目录。一份来源就是一份包含可编辑文献笔记区和受保护原文快照区的 Markdown 文件。
4. 输入附带链接时，想法进入闪念空间，正文 Markdown 快照和本地图片进入溯源空间，并双向链接。
5. 只有链接时，Agent 必须先阅读并提出内容相关的保存动机问题；用户回答后才持久化。放弃回答则零写入。
6. 默认只保存来源快照和待处理骨架，不自动生成作者观点或用户理解。
7. 永久卡片正式接纳前，用户必须用自己的语言重新解释；纯确认无效。
8. v0.1 七个核心 Skills 均需最小但真实可用；Skills 负责对话，CLI 负责确定性写入。
9. v0.1 仅供当前用户、macOS 本机使用；网页与微信公众号为首批来源，本地文件以后再做。
10. 每个成功原子事务自动创建 Git 提交；回滚使用非破坏性 revert。
11. Skills 位于项目内 `.agents/skills/`。
12. 真实验收包含 Karpathy gist、一篇公开公众号文章、用户本人一次保存动机和至少一张永久卡片的重新解释与接入。
13. 飞书概念说明 revision 30 与本文件共同构成 v0.1 基线；不回写飞书，执行期间不跟随新想法漂移。

## 2026-08-07 用户确认的基线修订

14. 永久卡片只能由用户主动发起；Agent 以一次一个问题的苏格拉底式对话帮助完善观点。用户授权后，Agent 可以删除口语停顿与重复、调整顺序、提炼标题并结构化为 Markdown，但不得增加新观点；全文必须经用户确认后才能写入。
15. 五个空间的内容文件统一使用 `YYYY-MM-DD-标题.md`。稳定 ID 只作为隐藏内部身份，不进入标题、文件名和人类可读索引。
16. Obsidian UI 配置纳入 v0.1 产品基线。机器参数继续服务 CLI 完整性、去重和状态机，但在 Obsidian 正常阅读界面中默认隐藏；稳定配置托管，临时 workspace 状态不托管。
17. [已由第 19 项覆盖] 溯源笔记只持久化规范链接；原始分享链接仅用于当次抓取。人类阅读顺序固定为“文章标题 → 原文快照 → 文献笔记 → 关联闪念”。
18. 正式卡片进入永久空间、索引和状态账本即视为接入卡片网络。首张卡片或暂时没有合适关联对象的卡片可以保持零语义连接；只有存在有意义的关系时才提出候选并由用户确认，不为完成流程强行造边。
19. 删除“文献笔记”这一认知层。溯源空间一份来源只保存来源元数据、原文快照、本地图片和机械维护的关联闪念；人的即时观点、疑问和念头进入闪念空间，连接并思考多个念头后形成的判断进入永久空间。此项修订覆盖冻结概念文档中关于文献笔记中间层的旧描述。

## 2026-08-09 用户确认的基线修订

20. 五个空间的正式内容与人类可读索引不保存或展示内容摘要，废弃 Frontmatter `summary` 字段。Git 事务中的同名操作说明只属于状态账本、日志和提交信息，不属于卡片内容。
21. 文档权威顺序固定为：`AGENTS.md` 定义人机权责，`schema.md` 定义机器可验证契约，项目 Skills 定义边界内的对话流程，`README.md` 负责解释，`.goodidea/baseline/` 保存历史依据。发生冲突时停止写入并交由用户决定。
22. 永久卡片由用户主动发起并确认完整草稿后，先通过 `permanent propose` 形成隐藏候选；只有用户随后明确要求正式创建，才能通过 `permanent accept` 进入永久空间。
23. 概念基线作为历史输入不静默改写；用户确认的后续修正追加在本文件，并同步当前 README、AGENTS、Schema、Skills、实现和测试。
24. 闪念捕获是独立入口阶段：用户想法是主信息，附件、链接和文件只是本轮想法的上下文。它们只做可访问性检查和按需读取，不能把主流程切换为来源摄取。
25. 一次捕获会话可以经过多轮交流产生多张闪念。系统先在不进入 Git 的运行时目录保护认知现场，再生成可反复修正的闪念候选清单；新增表达使旧候选和确认失效。
26. 用户确认最新完整清单已经覆盖本轮该记录的内容后，CLI 才原子创建正式闪念。会话支持暂停、恢复、放弃、失败重试和整批非破坏性回滚；永久卡片阶段不因本修订自动启动或改变。
27. 来源快照、图片、关系、索引和全库验证在捕获完成后通过可恢复后台任务执行。来源失败、图片失败、上下文变化和任务中断不得回滚正式闪念；新闪念可以在安全原子边界抢占后台维护。
28. 临时原始会话默认不永久托管。finalize 后只保留短期恢复窗口，来源维护完成且至少 24 小时后清理；正式闪念和来源继续进入聚焦 Git 历史。
29. 闪念以“一次被激活的认知事件”为记录单位，不强制一张只含一个孤立要点；同一事件可包含多个有清晰逻辑关系的内容。捕捉必须同时保留来源论证与出处、现实触发场景或卡点、当时观察到的现象与情绪，以及被激活的连接逻辑，不能把研究脉络拆成平铺清单。
30. 未经用户明确发起永久、母题、行动或索引卡片阶段，捕获对话不得使用定义、因果、证据、边界和反例等永久卡片式苏格拉底问题；捕获阶段只确认补充、修正、分组、合并、拆分、删除和完整清单。
31. 永久卡片形成与草稿审查属于同一正式卡片生命周期，由一个项目 Skill 负责；项目级核心 Skills 从七个收敛为六个，不再维护独立的 review-permanent 包和跨 Skill 交接。
32. 候选文件本身是待处理候选的唯一事实源，候选目录只保留 `pending` 文件；接纳或撤销后删除候选，其结果、原因和历史由事务账本、追加日志与 Git 保存，不再镜像到 `state.json.proposals`。
33. 来源文件的身份字段和稳定 ID 是来源身份唯一事实源；闪念的 `source_ids` 与正式卡片的 `derived_from` 是关系起点事实。来源 `flash_ids`、闪念 `converted_to` 和 `state.json.sources` 属于可推导镜像，统一废弃；人类可读反向链接由 CLI 生成。
34. 闪念陈旧性按读取时的创建时间动态计算，不持久化 `expires_at`，不设定时任务，不自动改变认知内容状态。仓库不再提供复制整套规则模板的公开 `init` 命令；开发测试从当前权威文件搭建隔离仓库。
35. 机器契约集中在 `src/goodidea/contracts.py`，实现、校验和测试共享类型、状态、ID、必填字段与时限定义；AGENTS、Schema、Skills 和 README 仍按不同读者保留必要说明，但不得各自创造机器规则。
36. Obsidian 正常阅读界面默认显示卡片 Frontmatter 属性，方便用户查看 ID、类型、标题、状态、时间和来源关系；这些属性仍由 CLI 独占维护，不授权在 Obsidian 中手工修改。本项覆盖第 16 项关于“默认隐藏机器参数”的显示决定，其他稳定配置托管与临时 workspace 不托管规则保持不变。

## 2026-08-11 用户确认的普通永久卡片准入修订

37. 当前只冻结普通永久卡片的准入标准，不把该标准提前扩展到母题、行动和索引卡片。普通永久卡片必须先成为一个可独立理解、中心判断明确、理由与边界足以接受未来质疑的用户认识，再进入网络激活。
38. 普通永久卡片必须至少连接一个真实、可寻址的形成来源后才能正式接纳；来源范围可以是闪念、外部来源、既有正式材料或本轮直接表达。外部依据由 `source_ids` 表示，形成来源由 `derived_from` 表示；同一来源可以同时承担两种角色，但两种语义不得混同。本项对普通永久卡片的要求覆盖第 18 项允许零连接接纳的旧决定；额外语义连接仍是可选的，不得强行制造。
39. 当普通永久卡片直接形成于本轮口述且没有既有可寻址对象时，CLI 在接纳事务中创建一个最小内部形成见证。见证只保存用户确认的一句有实际意义的形成情境及机械反链，不保存完整聊天原文，不制造闪念，不进入内容空间、索引、生命周期或独立 review。
40. 普通永久卡片的用户认知正文与系统导航区保持边界：用户确认草稿的文字和顺序不得被改写；CLI 可以在接纳时追加“形成来源”导航区，保存形成链接及直接表达说明。候选形成与正式接纳继续是两次独立用户决定。
41. 闪念作为普通永久卡片形成来源时，只有 `pending` 可在接纳事务中转为 `processed`；已为 `processed` 的闪念保持原状态和时间，`dismissed` 闪念不得被接纳流程静默复活。上述卡片、见证、闪念状态、候选删除、索引、日志和账本必须属于同一个可回滚事务。

## 2026-08-12 用户确认的基线修订

## 2026-08-13 用户确认的来源渠道标签修订

43. 来源渠道标签采用"回忆锚点"语义：来源 Frontmatter 新增可选 `tags` 字段，只存用户命名的高辨识度实体身份专有名词（渠道品牌/人物/系列场景），不存载体形态（可推导信息不存储，按需视图层派生）；打标签发生在保存来源的前台对话（顺口一问"这条你未来会用什么词想起它？"），后台来源维护不提问、默认不打；没有增量的来源允许不打；schema 只写弱约束（可选字段 + 字符串列表），全中文/去重/≤2 条由对话层查重维护；修正路径 = 重跑 `maintain source-tags`（传新值整体替换、传空列表清除），只改 frontmatter 不触碰快照。

## 2026-08-15 用户确认的待办状态归档

45. 待办按状态归档，一个状态对应一个文件夹：`待办空间/` 根目录存放 `进行中`，`待办空间/已完成/` 存放 `已完成`，`待办空间/已取消/` 存放 `已取消`。`capture transition` 流转状态时自动把卡片文件移到对应状态目录（已完成/已取消移入子目录，改回进行中移回根目录），并同步重写全库引用、索引与状态账本；所有扫描（lint/verify/review/maintain/find_note）同时覆盖根目录与两个状态子目录，归档卡片不脱离系统管理。同步修改 contracts.py（TODO_STATUS_DIRS）、notes.py（note_scan_dirs/note_scan_entries）、repository.py、service.py、schema.md、README.md 与对应测试。用户偏好：已完成事项不挡在行动队列里，档案由 git/log 承担。

## 2026-08-16 用户确认的待办生命周期时间契约

46. 待办卡片新增两个生命周期时间字段（与 `not_started_at` 同构）：`completed_at` 进入「已完成」时写入完成时刻、退出「已完成」时清除；`expired_count` 进入「已过期」时累计 +1（`capture transition` 手动与 `capture sweep` 自动同源），只增不减，作为承诺质量的负信号——反复过期即"不是真想做"，供 review 筛清理候选。分析口径：待办「念头诞生时刻」默认等于 `created_at`（用户通常实时想起即记录），表达内容中自述更早诞生时间的以内容为准。本轮明确不落 `due_at`（口头相对时间如"明晚/周末"解析成本高、收益不明）与 `started_at`（"开始行动"无清晰可观测锚点，用户自身亦难回答）。同步修改 schema.md、service.py（capture_transition/capture_sweep）、tests 与 README.md。
