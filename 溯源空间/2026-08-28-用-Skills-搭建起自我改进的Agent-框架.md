# 用 Skills 搭建起自我改进的Agent 框架

## 原文快照

<!-- goodidea:snapshot:start sha256=e88e10322a3aad267fe9d98721b6eaf6a733738aa5081684c5a51289ab1e39eb -->
> 发布日期：2026-08-28

Anthropic最近在它的博客里面分享了Warp的一套让 Agent 自我进化的方法。

核心思路很简单，用两层 Agent Skills 加一段人类反馈，搭出一个闭环，让 Agent 在使用中不断修正自己。

这套机制现在已经跑遍了 Warp 的整个开源仓库，写规格文档、代码审查、issue 分诊的 Agent，各自带着一套改进循环。

其实看下来整篇的思路和我现在已经完全不看AI写的代码了很像，可以结合这个文章作为对比参照以及实例demo。

为什么要自我进化？

起因是 Warp 内部的代码审查 Agent 出了问题，工程师抱怨它给出的评论没用，质量参差不齐。

开发团队最先想到的办法是人工改提示词、往 AGENTS.md 里补上下文，这种能临时使用有效果的，但是对于长期的大上下文来说捉襟见肘。

因为人给 Agent 的反馈，会话一结束就消失了。

同一个错误可能每周都要重新教一遍，想让 Agent 真正变好，得先解决反馈的持久性的问题，让错误不再重复。

自我进化的步骤

把这套机制拆开看，一共三层。

内层是基础 Skill。内容的是干活用的领域背景知识和判断标准，Agent 每次执行任务时都靠它生成结果。

中间是人类反馈。这是整个闭环里最关键的一环，而这个环节里面最重要的是能够说清楚问题的症结所在。

外层是改进者 Skill。这一层是全自动Skill脚本，按计划定时运行。

它做的是定期把攒下来的人类反馈拉出来，对比 Agent 当初的输出和人实际的反应，提出一处小而聚焦的修改，应用到基础 Skill 上。

其实原理很简单，就是把 GitHub 这一套工作流程搬到了 Skills 的自我进化当中，通过脚本的自动化形式，不断地将人类反馈进行收集提炼，最终形成一个完善的闭环。

等于是把Skill的更新迭代做成像普通代码一样开 PR、走审查、被合并，合并之后，然后基础 Skill 下一次运行就自动带着这次教训上路。

为了写好这两层 Skill，Warp 团队总结了几条心得。

一是基础 Skill 要写原则而不是写规则，同时要把原则背后的道理讲清楚。

二是反馈的采集门槛要压到最低，最好就在人本来就在的地方收集，比如直接在 PR 或 issue 下评论，不需要人额外多走一步。

三是Skill 本身要保持精简，引用资源文件和脚本，不把所有东西一次性堆进上下文。

四是改进者 Skill 尤其值得多花心思，因为它的复用性很强，换一个 Agent 场景，核心逻辑基本不用重写。

Warp 具体的实施步骤

Warp 的 issue 分诊 Agent 是这套机制落地最完整的例子，实际跑法是这样的。

比如有人开了一条新 GitHub issue，一个 GitHub Action 立刻触发分诊 Agent，让它判断复杂度、打标签、给出修复方向的建议。

这个 Agent 依赖的基础 Skill，存的是每个标签的含义，以及打标签之前该怎么去研究代码库。

某一次，Agent 判断得基本准确，但漏打了一个标签，叫 ready to spec，表示是这条 issue 已经具备让人动手写产品规格的条件。

又有一次，一位维护者发现了这个遗漏，直接在 issue 下面留言，说明了自己的判断和理由，这种既给结论又给理由的反馈，后续很容易被 Agent 消化掉。

外层的改进者 Skill 跑在 Warp 自家的编排平台 Oz 上，按计划运行的更新分诊任务。

它先登录 GitHub，执行一段随 Skill 打包好的 Python 脚本，把最近带反馈的 issue 拉出来汇总成一份 JSON，再把这份汇总读回上下文，这种把脚本打包进 Skill。

接下来，Agent 从维护者的留言里提炼出具体的反馈信号，提出能覆盖这些信号的最小修改，开了一个 PR，给基础 Skill 加上一条规则，只要问题本身描述清楚、是真实存在的，也应该打上 ready to spec 标签。

PR 里写明了是哪些反馈信号促成了这次修改、具体改了什么。

最后人来审核、批准、合并，下一次分诊 Skill 运行时，就带着这条新知识上路了。

结合到个人的使用

Warp 因为涉及到上万行的代码修改，全球又有几百号人贡献，这套机制比较适合于团队。

对于个人项目来说，其实也可以走这个流程，而且更简单。

大致分成几步走。

先把基础 Skill 写出来，一个最简单的形式，是一份带 frontmatter 的 Markdown，声明用途和触发时机，正文写具体判断逻辑：

---
name: code-review-base
description: Claude 帮我写代码或改代码时，用来自查的判断标准
---

# 代码审查基础规则

- 一个函数只做一件事，超过三十行就该拆
- 异步调用必须处理错误，不能用空的 catch 吞掉异常
- 调外部接口要设超时和重试，不能假设网络永远稳定
- 命名要和项目里已有的约定保持一致，不要自创一套风格

反馈这一步，可以自己在本地记一个文件就够了，每次觉得AI生成的代码哪里不对，随手写就行，当然也可以在Agent的对话的过程当中让它去复盘本次的对话经验踩坑总结：

skills/
  code-review-base/
    SKILL.md
  review-improver/
    SKILL.md              # 改进者技能，说明什么时候读反馈、怎么提出修改
    scripts/
      propose_update.py   # 读本地反馈和当前 Skill，生成一份修改建议
    feedback.md            # 自己随手记的反馈，不需要任何工具

review-improver/SKILL.md 里只写清楚触发时机和调用哪个脚本，具体脚本可以抄一下我现在已经完全不看AI写的代码了

---
name: review-improver
description: 定期检查 feedback.md，提出对基础 Skill 的最小修改
---

# 改进者技能

- 每次被要求"更新代码审查 Skill"时，运行 `scripts/propose_update.py`
- 脚本会生成一份修改建议，写在 `code-review-base/SKILL.proposed.md` 里
- 自己对比原文件看一眼再手动替换，不要脚本直接覆盖原文件

scripts/propose_update.py 是唯一需要的脚本，读本地反馈和当前 Skill。

最后一步还是交给自己，看一眼 SKILL.proposed.md 里改了什么，觉得对再替换掉原文件，顺手把 feedback.md 清空，等下一轮反馈继续攒。

单人用的好处就是这一步可以很随意，不用走审核流程，改动前自己看一眼就行。
