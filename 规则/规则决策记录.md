# 决策记录

本文件只记录规则为什么改变及其生效时间，不重复现行规则正文。

## 2026-09-25｜独立项目重建

- v0.16 在独立项目中从零建立，不在旧 Good Idea 仓库上继续叠加。
- 旧项目只作为历史数据和经验参考，不复用旧业务代码、旧 Skill、旧状态机和旧目录结构。
- 新项目首先明确数据层和规则层；Kernel 是机械支撑，Skill 与应用均可缺席。
- 结构设计以“简洁、灵活”为首要判断标准。

## 2026-09-25｜项目规则自成一体

- 原始设计方案是设计输入和历史材料，不是运行时权威。
- `规则/` 经审阅后成为项目自己的唯一权威规则层。
- 项目必须在移除原始设计方案后仍能解释对象、权责、协议、默认值和演化方式。

## 2026-09-25｜回到规则验证阶段

- 提前实现的 Kernel 与实现测试保存在 Git 分支 `prototype/kernel-v0`。
- `main` 暂不维护活动 Kernel，先完成场景推演和真实试运行。
- 只有真实使用中反复出现并能说明所减少摩擦的动作，才重新进入固化评估。

## 2026-09-25｜混合数据模式

- 原始思考、正式闪念、永久认识和来源记录以 Markdown 作为人类可读的认知事实。
- 本节中曾预留的 JSON 机械状态方案已被后文“移除机械层”决策取代。
- 真实试运行保存完整可见对话，不以匿名摘要替代。

## 2026-09-25｜认识与发酵语义纠偏

- 永久认识的生命周期只区分有效与停用；修订通过版本历史表达，不再作为生命周期状态。
- 发酵只要求一段忠实的自然语言备注，不设置强制三字段问卷。
- 48 小时保鲜期保留为可配置初始默认，不作为不可更改的硬边界。

## 2026-09-25｜Skill 保持未定

- 当前不创建正式 Skill。
- Skill 的数量、名称、文件结构和拆分方式都不是当前产品规则。
- 未来只有在真实使用证明存在稳定触发、路由冲突或上下文负担时，才讨论 Skill 包装。

## 2026-09-25｜两个核心 Skill 进入试运行

- 产品讨论明确了两个稳定且不同的认知意图：保护正在发生的认识，以及发展一个值得继续推敲的认识。
- 项目创建 `goodidea-capture` 与 `goodidea-distill` 两个轻量 Skill；它们只负责触发、规则加载、对话组织、停止和交接，不重新定义产品规则。
- 上下文召回和统一来源登记是可插拔能力，不增加核心 Skill 数量。
- 纯资料保存不触发捕捉 Skill；成熟判断可以直接进入沉淀 Skill，不强制先创建闪念。
- 两个 Skill 仍处于真实试运行阶段，可以根据路由冲突和上下文负担调整、合并或删除，而不改变对象身份和数据历史。

## 2026-09-25｜双核心 Skill 对齐时补全规则

- 这次规则修订来自双核心 Skill 产品定义与实施审查的对齐，不是已经由真实试运行反复证明的摩擦；因此相关行为仍需在试运行中验证，不能因写入规则就视为产品效果成立。
- 捕捉只接受用户明确的记录、捕捉、保存或续接意图。普通聊天中的明显认知种子只允许在自然停顿处建议一次；用户确认前不得创建会话、文件或正式对象，避免自动发现变成静默记录。用户确认后，可以保存确认明确涵盖的前序可见消息，既保住刚才的思考，又不扩大记录授权。
- 原始思考记录以松海明确发起的连续捕捉行为为边界，不根据对话中的语义分支实时拆分。这样优先保存认知发生的完整过程，把拆分和归纳留到表达结束后。
- 闪念候选允许包含人机共同推理中真正形成的新理解，但必须和原始对话分开显示，并继续由用户决定是否认领，避免把“非逐字摘录”误判为“Agent 可以替用户立场”。
- 正式闪念增加最小语义要求，是为了能够重新唤起内容、注意它的原因和形成现场；这些语义由 Agent 从对话中保护，不转化为要求用户填写的表单。
- 闪念辨析明确先判断是否值得继续投入，再决定是否完善，避免语言润色和信息补齐替代价值判断。
- 认识完善的问题数量由真实认知缺口决定；理由、其他解释、边界、反例、不确定性和未来作用都只是可能维度，不构成固定问卷。
- 旧项目中的母题和其他非核心内容只作为只读历史上下文，因为新项目不把旧分类继续固化为 v0.16 对象或写入口。
- “小/大、清晰/模糊”的干预矩阵进入可调启发式，是为了减少打断而不是规定流程；用户仍在表达时，矩阵必须让位于当前对话。
- 捕捉结束时，只有用户主动要求或确有清晰认知种子才询问闪念候选，避免把每次记录都推向加工和转化。
- 项目使用 `.agents/skills/` 是为了遵循当前 Agent 平台的项目级 Skill 包装约定。复用目录位置和 `goodidea-` 命名前缀不代表继承旧项目架构；对象、规则、流程和实现仍由本项目独立定义。

## 2026-09-25｜试运行完整对话按对象身份分流

- 捕捉类试运行已经产生原始思考记录，完整对话继续以 `数据/记录/闪念/原始思考记录/` 中的 Markdown 为唯一事实；试运行记录只引用它并保存观察。
- 辨析、认识完善、召回和来源登记等非捕捉试运行不伪造原始思考记录。其完整可见对话直接保存在对应的验证记录中，作为评测证据。
- 验证记录不是正式认知对象，也不能替代正式闪念、永久认识、来源或它们的形成依据。

## 2026-09-25｜旧数据按新契约分批迁移

- 旧项目继续只读保留，但允许把逐项登记、完成对象转换并通过验证的旧数据复制进新系统；禁止整库原样倾倒。
- “有意思”成为正式内容对象，用于承接值得留下但尚未认领为闪念、永久认识或保存为完整外部来源的内容。
- 正式 Markdown 的状态统一使用中文；旧项目待处理闪念迁入后保持 `待处理`，不追溯执行保鲜期限。
- 旧项目原始思考记录和讨论日志不迁移；正文中已有的真实触发情境继续保留。
- 本节采用过的“日期＋序号＋标题”和内部 ID 方案，已被后文“移除机械层”决策取代。
- 首轮按有意思、闪念、永久认识、外部来源各迁移 10 条，验证实际阅读效果后再决定是否继续。


## 2026-09-25｜移除机械层

- 当前项目不使用活动 Kernel、索引、缓存、操作事件或独立对象 ID；机械层没有实际调用方，因此从正式系统中移除。
- 正式内容只保留人类阅读所需的 Markdown 事实。迁移脚本和首批清单降为 `数据/旧项目/迁移历史/` 下的历史材料，不参与日常运行。
- 正式文件采用 `YYYY-MM-DD-标题.md`；只有同日同标题冲突时才追加最小区分后缀。
- 关联只表达“为什么有关联”，并在原因中附对应文档链接；不展示独立 ID、哈希或机械依赖清单。
- 原始思考记录归入 `数据/记录/闪念/原始思考记录/`，是闪念生成过程的记录，不是与闪念并列的正式对象。

## 2026-09-25｜外部来源回归带出处的原文

- 实际阅读发现，原始引用、规范身份、别名、快照时间和获取方式虽然结构规范，却没有帮助理解材料，仍在延续机械审计层。
- 外部来源因此收缩为客观属性与实际内容；正常情况不记录获取过程，异常只在确实影响理解时说明。
- 同一材料的修订历史由 Git 承担，不再在单张卡片内维护快照历史。

## 2026-09-25｜全部正式内容回归当前人类阅读层

- 对其余三类对象继续应用同一原则：卡片只回答“现在保存了什么、为什么值得理解、后来实际去了哪里”，不保存系统如何管理它。
- 有意思、闪念和永久认识移除状态字段、创建时间账本与状态历史；只有真实去向存在时才用自然语言说明，没有决定就不放占位状态。
- 永久认识正文直接呈现当前判断。松海认领修订后更新当前正文，旧版由 Git 保留；卡片内不再复制整套版本档案。
- 时间可以触发回看，但不能自动制造“失效”结论。原始思考记录的起止由实际消息时间和对话本身呈现，不另建开关字段。
