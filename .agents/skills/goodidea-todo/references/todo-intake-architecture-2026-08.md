# 待办摄入架构（2026-08 拍板背景与详解）

> 本文档是 goodidea-todo 的低频知识附档。操作要点见 SKILL.md 正文；此处保留拍板背景、消费方详解与教训案例，供需要时回溯。规则语义与 capture-flash 拆分前完全一致（2026-08-23 搬迁，未改任何规则）。

## 四段信息架构的消费方（2026-08-16 实测拍板：为消费方写作）

`capture todo` 落库四段各有消费方，写每段前先问"谁在什么时刻读这段"，不填模板：

| 段 | 参数 | 消费方 | 写作要求 |
|---|---|---|---|
| 标题 | `--title` | 人扫数据库表格 | 短索引（≤15 字、行动导向），一眼定位；**必须显式传短标题**，CLI 缺省会取 text 首行前 40 字（过长，2026-08-16 被纠正） |
| 事项 | `--text`（「原始记录」区） | 执行者 | **结构化提炼，不是口语原样**——口头表达是素材不是成品 |
| 动机 | `--reason`（「为什么做」区） | 估价 cron 与裁决者 | 用户确认的动机原话或提炼 |
| 情境 | `--context`（「产生情境」区） | 回顾者 | **现场还原**——触发时刻 + 当时语境 + 鲜活细节 |

## 事项段：语义折叠复现（2026-08-16 曾鸣卡案例）

先解码口述的语义折叠（行动/对象 → 焦点 → 价值 → 成本），复现折叠结构分层写；内容忠实（观点不增不减）、形式加工（去口语填充，保留关键细节，用户原话金句可加引号）。**口述含多层语义折叠时平铺即失败**（案例：整本书→第一章→一个底层逻辑→一个可复用算法，复现折叠后用户判定"不错"）。

## 情境段：禁止干瘪元数据（2026-08-16 纠正）

只写书目/链接/清单出处属于干瘪描述（被纠正"不够鲜活"）。要求：触发时刻 + 当时语境 + 用户原话里的鲜活细节（时间/场景/原话引述），一眼看懂"为什么此刻想起"。

## 摄入澄清 B 原则（2026-08-15 拍板：模糊才问）

用户口述已含动机/价值/时间信息的，直接存不追问——全问会制造流程摩擦；只有一句话、意图不明、无动机信息的才追问。追问方式：一次一个问题的对话式提问（不是表单），按序使用四问（为什么做/不做会怎样/做完是什么样/打算什么时候做）。用户回答的原话（经用户确认）作为 `--reason` 写入「为什么做」区；未追问的直接从口述中提炼动机并请用户确认后写入。`capture todo --reason` 可选参数，缺省不报错。估价 cron 会先读「为什么做」区作为判断依据。

## CLI 参数映射（2026-08-16 实测）

`capture todo` 支持 `--title`/`--text`/`--context`/`--reason`/`--source-id`。不凭旧习惯把 text 当标题——系统设计信号（参数分离）就是正确结构。

## 48h 行动窗口（2026-08-15 拍板）

新建默认「未开始」，48h 内开始做（改「进行中」）即通过；超 48h 未动会被 `capture sweep` 转「已过期」，需重新承诺（写原因）或干掉。48h 是开始行动的窗口不是完成期限。完整机制见 `设计方案/待办行动闭环v2实施任务.md` 与 schema.md。
