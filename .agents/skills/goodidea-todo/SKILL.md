# 记录与管理待办

先读仓库根目录的 AGENTS.md 与 schema.md。待办是行动承诺，不是想法；用户表达待办事项、任务、行动承诺时进入本 Skill。

## 触发与排除

- 触发：用户表达待办/任务/行动承诺（含"记一下/放到待办"）；用户在 Obsidian 待办数据库视图手动改过状态需要收口；待办需要摄入澄清或 48h 窗口提醒。
- 排除：用户正在表达、补充、修正或审阅闪念想法（即使附带待办意图）→ 交给 goodidea-capture-flash 主导；有意思内容 → 走 `capture interesting`（capture-flash 轻量记录）。

## 摄入流程

1. **B 原则（模糊才问，2026-08-15 拍板）**：用户口述已含动机/价值/时间信息的，直接存不追问——全问会制造流程摩擦；只有一句话、意图不明、无动机信息的才追问。
2. 追问方式：**一次一个问题的对话式提问（不是表单）**，按序使用问题集：
   1. 为什么做这件事？（动机/价值 → 喂需求类型+高阶目标）
   2. 不做会怎样？（损失/机会成本 → 喂值不值得）
   3. 做完是什么样？（期望产出 → 喂具体性）
   4. 打算什么时候做？（时间窗口 → 喂距离+投入规模）
3. **CLI 参数先查（2026-08-16 实测）**：摄入前先核对 CLI 字段映射（`capture todo` 支持 `--title`/`--text`/`--context`/`--reason`/`--source-id`），不凭旧习惯把 text 当标题——系统设计信号（参数分离）就是正确结构。

       uv run goodidea --root <仓库> capture todo --title <短标题> --text <事项> --context <情境> --reason <动机>

4. **四段信息架构要点（2026-08-16 拍板，详见 references/todo-intake-architecture-2026-08.md）**：写每段前先问"谁在什么时刻读这段"，不填模板——
   - 标题（`--title`）：短索引（≤15 字、行动导向），供人扫数据库表格一眼定位；**必须显式传短标题**，CLI 缺省会取 text 首行前 40 字（过长）。
   - 事项（`--text` → 「原始记录」区）：**结构化提炼，不是口语原样**——复现口述的语义折叠分层写；内容忠实（观点不增不减）、形式加工（去口语填充，保留关键细节，原话金句可加引号）。口述含多层语义折叠时平铺即失败。
   - 动机（`--reason` → 「为什么做」区）：估价判据，估价 cron 先读；用户确认的动机原话或提炼。
   - 情境（`--context` → 「产生情境」区）：**现场还原**——触发时刻 + 当时语境 + 用户原话里的鲜活细节，一眼看懂"为什么此刻想起"；禁止干瘪的元数据式描述。
5. 用户回答的**原话**（经用户确认）作为 `--reason` 写入「为什么做」区（属于用户认知正文，非 CLI 机械区）；未追问的直接从口述中提炼动机并请用户确认后写入。`--reason` 可选参数，缺省不报错。

## 48h 行动窗口提醒

存待办后提醒用户：新建默认「未开始」，48h 内开始做（改「进行中」）即通过；超 48h 未动会被 `capture sweep` 转「已过期」，需重新承诺（写原因）或干掉。已在数据库视图灰显置底呈现。48h 是开始行动的窗口，不是完成期限。

## 状态收口（阅读层手动改状态后）

用户在 Obsidian 待办数据库视图直接改过 `status` 后，走 CLI 收口（只确认意图，无对话流程）：

- 单条：`uv run goodidea --root <仓库> capture transition --id <ID> --status <状态> --accept-dirty`
- 批量：`uv run goodidea --root <仓库> capture sync`

## 边界

- 估价由 cron（每 8 小时）自动执行，本 Skill 不主动估价；估价依据读卡片「为什么做」区。
- 状态机、归档目录（未开始/进行中/已过期/已完成/已取消）、48h 过期规则由 CLI 与 schema.md 定义，本 Skill 只负责对话流程。
- 正式记录完成后运行 goodidea lint；批量收口后运行 goodidea verify。
