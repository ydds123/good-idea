# Good Idea 仓库操作（Agent 侧）

在 `~/Documents/Goodidea` 里改规则、维护标签、与松海做捕捉和讨论时的操作手册。

本 Skill 与 `goodidea-source-sync`、`goodidea-capture`、`goodidea-distill` 同属本仓库 `.agents/skills/`，仓库是唯一副本；Hermes 侧通过 `skills.external_dirs` 指向该目录全局加载（配置在 `~/.hermes/config.yaml`），`~/.hermes/skills/` 下不再保留副本。

## When to Use

- 松海要改 Good Idea 的规则、规则结构，或 `规则/` 下文件的归属与去留；
- 要新增／引用／停用标签，或跑标签体检；
- 要进入一次捕捉、辨析或方案讨论（先把他的思考、外部来源、项目文件分开摆出来）。

不适用：来源登记的取料、落盘、合并、去重命令走 `goodidea-source-sync`；闪念与永久卡片的对象语义以仓库 `规则/` 为准。

## 边界（先读）

- 规则权威一律在仓库 `规则/`（`系统宪法.md` 最高）；本 skill 只写操作、指针和协作规矩。**不在这里复制规则正文**——冲突时以规则为准，复制等于制造第二套规则。
- `规则/` 与 `数据/` 两层就够：规则层回答“应该怎样”，数据层只回答“已经保存了什么”。`验证/` 记录真实使用中的试运行观察，方式以 `验证/试运行协议.md` 为准：捕捉、辨析、来源登记这类真实事件要写；**规则或文档改动本身不另写试运行记录**。
- 规则或流程的实质改动记进 `规则/规则决策记录.md`（原因 + 生效），并保证 `规则/README.md` 职责表里的单一归属仍然成立；没定稿的讨论不沉淀、不落文件。
- 改完直接 git 提交（AGENTS.md 允许）；**推送只在松海明确要求时做**，推完回读验证：`git ls-remote origin refs/heads/<分支>` 拿到新 sha，再用远程树逐文件比对确认远程 == 本地——只看 `git push` 的输出不算验证完。`.obsidian/workspace.json` 是 tracked 文件、仓库惯例是随状态一起提交（tip 提交即「同步 Obsidian 工作区状态」），默认别为「干净」把它排除；**但松海明确要求豁免时就照办（典型场景：执行他给的工单，要保证每个提交只含本阶段文件）——不提交、不 stash、不 checkout，每个提交只 `git add` 自己新建／改动的文件**，冲突时以他当次指令为准。`.obsidian/` 下其他文件不主动碰。
- 查远程同步状态**不靠 fetch**：`git ls-remote --heads origin` 看各分支 tip；比提交差异用 `gh api repos/ydds123/good-idea/compare/<base>...<head>`（status/ahead_by/behind_by ＋ 提交与文件清单一次拿全）；比文件差异用 `gh api "repos/ydds123/good-idea/git/trees/<ref>?recursive=1"` 取远程 path+blob sha，再在本地算 git blob 哈希对比——**零对象下载**，几秒出结果。命令、坑与现成脚本见 `references/remote-state-check.md`。
- 这个 clone 的 fetch refspec 只配 `refs/heads/v0.16`，本地根本没有 `origin/main`；**不要 `git fetch origin main`**——走代理拖几百个对象、几 KB/s 到卡死（`curl 18 partial file`）。默认只看 `v0.16`；松海点名 main 时按上面 API 路线答，仍然不 fetch。
- 对比类请求（「远程是不是最新的」「本地和远程差多少」）**一轮给结论**：先给 ahead/behind 数字 ＋ 差异文件清单（按目录汇总），再给一句下一步选项；不要把网络探测、fetch 进度、命令输出摊给他看，也别为这一个结论分多轮汇报。
- 规则层现在是机制与内容分家：`规则/标签树.md` 放机制（线怎么划、进树条件、边界例、层级、退场），`规则/标签清单.json` 放取值清单（`tags` 允许值的唯一来源）。分家理由：机制少变、清单常长。**加标签只改清单、单独提交，再写进材料**；只有机制改动才算规则演化。

## 标签维护（新增、引用、退场）

- 线的划分、进树条件、闸门、层级条件与退场标准全部以 `规则/标签树.md` 为准，取值与字段格式以 `规则/标签清单.json` 为准（清单结构见该文件自身的「格式」节）；本 skill 不重复定义，改机制改规则、不在这里改。
- 只写规则里没有的操作要点：**用途线的判断权在松海**——Agent 只给候选，不主动猜用途；材料「与某件事相关」属于主题线。
- 判主题／判标签**不要靠词频**：一次清扫里四个候选主题在 10/11 份材料里都高频命中，词频没有区分度——逐份读材料的「智能总结」再判，份数汇总交给体检命令。
- 引用与体检的命令、落盘形状、一晚多段录音合并、去重规则见 skill `goodidea-source-sync`（细节归它，本 skill 不重复）。

## 执行工单与回报

- 他给一份执行任务书（通常在 `文档/临时/…执行任务.md`）时**按原文执行**：不自行扩项、不跳步、不改阶段顺序；某阶段只有源码级证据、还没真实回合证据时停下来报告，不猜、不伪造数字。（其硬要求：不得猜测格式、不得伪造性能数字、无真实证据必须暂停并报告。）
- 每个阶段单独提交；提交说明写清：改动、实际核实结论、改前/改后数字（适用时）、未完成项与暂停原因、偏离方案及原因；除明确要求外不 push、不碰 main。
- 阶段产物（探针、验收证据、性能测量）落 `文档/临时/` 或仓库既有位置，不为它新建目录结构。
- 回报用他给的结构化模板逐项填满：**真实路径、commit ID、可复核的验收证据、原始数字**——只写「已完成」不算证据；涉及 Hermes 配置/日志的内容先脱敏（去 token、密钥、私人对话、回复正文）。
- 会写产品数据的链路（捕捉、来源登记）先在 `git clone` 的沙箱里跑验证，真仓库测后立即 `git status --short` 核对并清理测试残留。

## 读取与效率

- 规则文件**按节读**，不要整份读：一次捕捉要读的规则总量约 27 KB，整份读完会拖慢每一轮。
- 材料先读结构（智能总结＋章节概要）再按需读正文——11 万字的播客读前 160 行就足以支撑一次讨论。
- 一轮耗时主要在**生成量**（输出 token ÷ 吞吐）与往返次数，不在「重放整场历史」：实测输出侧 ≈74%、未缓存输入的预填 ≈2%。能批量就批量（每次往返都自带一份输出与固定开销），并先砍答复长度；历史瘦身是次要项。**评估这类性能主张先回原始日志核算**——命令、归因方程与判定表见 skill `hermes-deployment-ops` 的《每轮耗时逐段记账》参考文件（turn-latency-accounting）。
- 长讨论变慢时，先换会话 + 用项目里的记录续接；不要用缩短回答深度来换速度（输出预算档位由松海定，Agent 不自己拍）。

## 与松海讨论（捕捉、辨析、方案讨论都适用）

- **先分层再讨论**：把他自己的思考、外部来源、项目文件分开摆出来；外部来源按广义理解（相关的项目文件也算一份来源）。
- **不要只做判断**：结论之外要给机理（构成 + 协作），并把他推翻的空间留着。
- **一次只推进一个关键问题**，一次给一个决定。
- **参与下限**：一个判断的框架与最终选择都要出自松海（直接或间接）。Agent 给出没有被他的框架支撑的选项，就等于占了「选项形成」的位置，他只剩打勾。要提自己的框架就显式举手（「我认为框架这里少一块」），不要悄悄换掉框架再端上选项。
- 属于他领地的判断（用途标签、认领闪念／永久卡片、状态改变）只给候选和理由，不替他定。
- 他说「只记录」就停止加工；说「先到这」按可续接封存（原样保存可见对话，末了不要再加新动作）。
