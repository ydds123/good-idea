# Good idea Skill 资源边界重构方案

> 文档性质：可执行的第一阶段试点方案，不是现行 Skill 或数据契约。
> 当前版本：v0.2-confirmed
> 形成日期：2026-08-11
> 当前状态：已获用户确认，进入 `goodidea-form-permanent` 安全试点

## 一、目标

当前 `goodidea-form-permanent/SKILL.md` 同时保存语义工作流与完整 CLI 参数配方。本试点只验证：

> 让主 Skill 保留触发、作者权、分支、用户决策点和停止条件，让 CLI `--help` 承担准确的技术接口后，Agent 是否仍能可靠完成永久类卡片流程。

第一阶段不评价其他五个 Skill，也不建立长期 Skill 治理体系。

## 二、唯一事实源

| 资源 | 唯一职责 |
|---|---|
| `AGENTS.md` / `schema.md` | 作者权、产品规则、状态、数据与事务不变量 |
| `SKILL.md` | 触发与排除、认知工作流、分支、用户决策点和停止条件 |
| CLI parser / `--help` | 参数名、输入类型、适用范围、确认语义和准确调用方式 |
| tests | 验证上述边界，不创造新规则 |

同一事实只保留一个权威定义；其他文件可以引用或验证，但不维护第二份完整定义。

## 三、第一阶段改动

1. 审计并补齐 `permanent propose/accept/withdraw/revise/feedback --help`。
2. 从 `goodidea-form-permanent/SKILL.md` 删除完整参数排列，保留命令阶段名称和执行前查看 `--help` 的要求。
3. 调整 Skill 契约测试，不再要求完整 flag 位于主 Skill。
4. 增加 CLI help 与 parser 的直接测试。
5. 在 disposable 临时仓库验证 propose 与 accept 的机器门禁；真实 Agent 两回合停顿另按第六节验收。

本阶段不新增 `references/`、`scripts/`、capabilities、机器协议、模板或治理目录。只有真实执行证明单个命令 help 清楚、但跨命令组合仍不可靠时，才评估最小 reference。

## 四、主 Skill 不可删除的语义

- 只有用户主动发起永久、母题、行动或索引卡片时才进入；普通想法和“以后可以成卡”不触发。
- 用户拥有中心判断和正文作者权，Agent 不新增观点；结构化前必须获得授权。
- 一次只问一个最关键的问题，完整草稿必须展示并由用户确认。
- 普通永久卡片必须满足中心判断、独立理解、理由、边界和真实形成来源门禁。
- 外部依据不等于形成来源；只有本轮直接表达可用时，不伪造闪念、不保存完整聊天。
- 完整草稿和形成来源确认只授权 `propose`。
- `propose` 后报告候选并结束当前 Agent 回合，不得继续 `accept`。
- 只有用户看到候选结果后发送新的明确创建指令，才允许 `accept`。
- 错误或过时候选必须撤销；`revise` 和 `feedback` 只接受用户本人提供并确认的内容。

## 五、从主 Skill 移出的技术细节

- `uv run goodidea --root <仓库>` 后的完整参数排列；
- flag 的精确组合、类型、默认值和适用范围；
- 文件路径、stdin 和转义细节；
- propose、accept、withdraw、revise、feedback 的完整调用配方。

主 Skill 可以保留 `permanent propose` 等阶段名称，因为它们表达不可省略的状态阶段，而不是参数手册。

## 六、验收

### 自动化边界

- 五个子命令的 `--help` 准确说明输入是路径还是文本、确认参数代表的用户决策和类型适用范围。
- 主 Skill 不再包含完整写命令，但仍能发现对应 `--help`。
- 作者权、形成来源、候选后停止、再次确认、撤销和用户修订语义仍在主 Skill。
- CLI 缺少形成来源或确认时继续拒绝；候选接纳、正文哈希和事务门禁不退化。

### 真实两回合行为

在 disposable 临时仓库中执行：

1. 用户确认完整草稿和形成来源后，Agent 只调用 `propose`，报告候选并结束回合；工具轨迹中没有 `accept`，永久空间没有新卡片。
2. 用户看到候选后发送新的明确创建指令，Agent 才调用 `accept`；随后候选删除、正式卡片创建、正文保持确认版本并通过 `verify`。

“草稿没问题”“形成来源没问题”“先生成候选”“我看到了”以及候选形成前的提前授权，都不能替代第二回合的新创建确认。

自动化字符串测试和 CLI 布尔 flag 只能证明静态契约与机器门禁，不能冒充真实用户轮次；没有真实两回合证据时，只报告实现完成，不宣称行为验收完成。

## 七、实施顺序

1. 补齐 CLI help 及其测试；
2. 精简主 Skill 并调整 Skill 测试；
3. 同步 README 的资源说明；
4. 运行定向 CLI、Skill 和永久卡片门禁测试；
5. 因涉及公共 CLI 与跨层契约，运行全量回归和官方 Skill 校验；
6. 审计差异与工作区边界；
7. 完成真实两回合行为验收后，再判断第一阶段是否通过。

如果 `description` 和任务路由未改变，不把路由评测列为必需门槛。

## 八、暂不处理

- 其他五个 Skill 的资源迁移；
- 是否增加 reference；
- `--confirm-user-authored` 兼容参数的弃用；
- `--from-ids` 与 `--direct-source-file` 是否应由 CLI 强制互斥；
- 通用机器能力、模板和自动化 Agent eval 基础设施。

这些事项不影响第一阶段判断，只有真实使用证据或独立产品决策出现后再处理。
