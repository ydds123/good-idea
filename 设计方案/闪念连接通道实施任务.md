# 闪念连接通道实施任务

## 文档性质声明

本文件是任务交接说明，不是生效规则；执行 Agent 不得放宽 AGENTS.md/schema.md/用户作者权边界。所有改动需符合仓库宪法、聚焦提交与既有测试契约。

## 一句话任务

为 good-idea 增加闪念卡片的直接连接通道：允许 **闪念↔闪念** 与 **闪念↔溯源（来源）** 两类连接组合，复用现有 `connect propose/accept/withdraw/disconnect` 命令与账本机制；其余组合维持现状（正式卡↔正式卡已有，正式卡↔闪念/溯源、溯源↔溯源暂不开放）。

## 背景与现状（已有机制盘点——"不要重复造"清单）

- 现有 `connect` 四命令全流程已实现：`connect_propose`（service.py:3021）→ `connect_accept`（service.py:3076，双向写正文"连接"节 + `state.json connections` 账本）→ `connect_withdraw`（service.py:3137）→ `connect_disconnect`（service.py:3168，移除正文节 + 账本）。
- 唯一硬校验：`connect_propose` service.py:3036-3039 的 `type not in PERMANENT_CARD_TYPES`（contracts.py:20 = {"permanent","mother","action","index"}）——闪念/来源被拒的根源。
- 正文写入已通用：`add_list_item_to_section`（notes.py:222）对不存在的"## 连接"节自动创建（追加到文件末尾）；`remove_list_item_from_section`（notes.py:238）对应移除。闪念正文（触发情境/闪念内容/激活逻辑/来源与论证锚点/演化记录）与来源正文（标题/原文快照/关联闪念）都可无损加节。
- 哈希契约已验证安全：来源卡 `snapshot_sha256` 只覆盖快照区（`<!-- goodidea:snapshot:start -->` 到 end，notes.py:94 `validate_source_note` 校验）；`content_sha256` 是抓取内容哈希（service.py:1766/1795，`preview.markdown`），与正文文件无关。来源正文加"连接"节不破坏任何哈希。
- 归档重写已覆盖：`_relocate_note`（service.py:824）与 `capture_sync`（service.py:864）全库 wikilink 重写会更新连接节里的链接（来源快照区受保护 `protect_snapshot=True`，但快照区外的"关联闪念"/"连接"节照常重写；被移动卡片自身正文也应用替换）。
- CLI 层对 `--from-id/--to-id` 无类型限制（cli.py:451-471），账本结构、候选文件（`.goodidea/proposals/connections/<PRP>.md`）、两阶段确认流程均复用。
- lint 对来源只跑 `validate_source_note` + 字段检查（service.py:3320-3330 附近），不校验节结构——加节不触发 lint 失败。

## 用户确认的设计（2026-08-20 拍板）

1. **连接端点范围**（用户原话级表述）：「闪念卡片可以和其他类型的闪念卡片做连接，也可以和溯源卡片做联动。其实我想让各种类型的卡片都支持双向连接，但是目前还没有出现这样的需求场景，所以先就闪念卡片和溯源卡片做连接吧。」→ 本次实现组合矩阵：
   - ✓ 闪念 ↔ 闪念（新）
   - ✓ 闪念 ↔ 溯源（来源）（新）
   - ✓ 正式卡 ↔ 正式卡（现状保留，任意正式卡类型之间互通）
   - ✗ 正式卡 ↔ 闪念 / 正式卡 ↔ 溯源 / 溯源 ↔ 溯源（暂无需求场景，不开放）
   - 设计应面向"以后放开更多组合"的愿景：组合矩阵写成可扩展的配置（如契约层连接图），扩展时改配置即可，不散落硬编码。
2. **闪念被永久卡接纳（转「已处理」归档）时连接的处理**：选择方案 A——**连接跟随闪念保留**，不继承迁移到永久卡。连接是卡片的属性，归档不销毁；永久卡的形成来源本来就指回闪念，认知网络不丢。语义延续由用户手动为永久卡建连接。
3. 默认项（用户未反对，视为确认）：正文节名与永久卡同款「## 连接」；关系类型沿用自由文本 + 理由必填（propose 时 rationale 必填）；复用 connect 四命令，不新增 CLI 命令/参数。
