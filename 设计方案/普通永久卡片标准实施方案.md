# 普通永久卡片标准实施方案

> 文档性质：普通永久卡片标准的实施与验收记录。本文不是正式永久卡片；现行规则以 `AGENTS.md`、`schema.md` 和项目 Skills 为准。
>
> 当前版本：v0.3-implemented<br>
> 形成日期：2026-08-11<br>
> 当前状态：用户已授权实施；权威契约、Skill、CLI、Lint 和测试已经同步

## 一、目标和边界

本次只解决一件事：

> 一张普通永久卡片只有在内容合格、形成来源真实可追溯，并已通过形成来源建立至少一条真实连接后，才能进入永久空间。

本次只约束 `type: permanent`。母题、行动和索引卡片继续沿用现行规则；最小任务调用闭环、关系词表、演化模型、Review、检索和派生视图均不进入本次范围。

实施依据是 [《普通永久卡片标准》](普通永久卡片标准.md)。实现复杂度不是目标，只实现上述门禁真正运行所需的最小机制。

## 二、普通永久卡片的接纳条件

### 1. 节点内容合格

形成 Skill 依次检查：

1. 用户已经用自己的语言形成认识，而不是复述材料；
2. 卡片只有一个明确的中心判断；
3. 脱离原始对话和来源后仍能独立理解；
4. 包含理解该判断所需的最低充分信息；
5. 能够在未来任务中被调用或继续发展；
6. 不存在会导致明显误用的关键歧义、隐藏前提或边界缺失。

未通过时继续一次一个问题地澄清，不生成候选。通过只说明节点本身合格，不等于获得正式创建授权。

### 2. 形成来源可追溯

形成来源回答“这张卡片从什么问题、经验或认知材料中发展而来”。外部依据回答“什么材料支持或检验这个判断”。两者不得混用。

- `source_ids`：只表示外部依据，不单独满足形成来源门禁；
- `derived_from`：表示形成来源，是网络激活所依据的关系；
- 外部来源如果确实参与形成判断，可以同时出现在 `source_ids` 和 `derived_from`；
- 闪念和其他已有认知材料作为形成来源时进入 `derived_from`。

所有 `derived_from` 对象都必须真实存在，并由用户确认其确实参与了当前判断的形成。

### 3. 直接口述形成最小来源见证

用户直接主动口述永久卡片时，不要求先人为创建闪念，也不保存完整聊天原文。系统只要求用户确认一条简短的形成说明：

> 这张卡是在回应什么问题、经验或现实情境时形成的？

这条说明必须具有实际语义，不能只是“来自本轮口述”“用户说过”或纯确认文本。它的作用是让未来仍能理解这张卡为什么会出现，并提供一个真实、可寻址的连接端点。

系统为其创建一个内部的“形成来源见证”：

- 具有稳定 ID；
- 保存用户确认的形成说明；
- 保存对应候选和最终草稿的内容哈希；
- 与正式卡片形成双向可校验关系；
- 不保存完整聊天原文；
- 不进入五个内容空间、人类索引或 Review 队列；
- 不设置生命周期、状态机或后续维护流程；
- 只由 CLI 在接纳事务和非破坏性回滚中维护。

它是内部来源记录，不是新卡片类型，也不是新的知识内容层。

用户确认的是形成说明原文。CLI 可以把这段原文机械包装为链接，放入卡片的“形成来源”系统维护区。该区域与 Frontmatter、反链和连接区相同，不属于用户认知正文；CLI 不得改写形成说明或增加新的判断。

### 4. 至少存在一条真实连接

普通永久卡片正式接纳时，`derived_from` 必须非空，并且每个端点都可被 CLI 寻址：

- 已有闪念、外部来源或其他正式认知材料，直接使用其稳定 ID；
- 本轮直接口述，使用接纳时创建的来源见证 ID。

布尔声明、标签相同、主题相似、只有技术引用或无法说明形成作用的关系都不能通过门禁。

进一步的支持、冲突、限定、例证、演化或行动验证关系仍由现有 `connect` 流程在接纳后按需建立，不是本次接纳事务的必经步骤。

## 三、人类确认顺序

必须保留两个可区分的用户决策时点：

1. Agent 展示完整认知草稿和形成来源说明，用户确认两者准确；
2. CLI 只创建待处理候选；
3. Agent 报告候选标题、形成来源和草稿身份；
4. 等待用户在候选已经存在以后，明确要求正式创建；
5. CLI 才执行正式接纳。

不能用用户在候选创建前的一句“可以”连续触发 `propose` 和 `accept`。用户确认形成说明后，接纳时不再为 CLI 的机械链接包装增加第三轮内容确认。

CLI 只校验确认参数、来源端点、候选状态和内容哈希，不替用户判断观点或关系是否正确。

## 四、最小数据和命令改动

### 1. 复用现有字段

继续使用：

- 候选中的 `source_ids` 和 `from_ids`；
- 正式卡片中的 `source_ids` 和 `derived_from`；
- 现有 `authoring_mode`、`draft_sha256` 和全文确认门禁。

调用时：

- 外部依据放入 `source_ids`；
- 所有形成来源放入 `from_ids`，接纳后写入 `derived_from`；
- 一个外部来源可以因同时承担两种作用而出现在两个列表中。

`from_ids` 只能引用仓库中具有稳定 ID 的正式认知材料或内部来源见证，不能引用待处理候选、事务或任意字符串。

### 2. 直接表达来源输入

`permanent propose --type permanent` 增加一个短文本文件参数，用于传入用户确认的形成说明：

```text
--direct-source-file <临时文件>
```

该文件不是完整聊天记录，只包含一条有实际意义的形成说明。候选保存其规范化文本和哈希，尚不创建正式来源见证。

所有普通永久卡片候选还必须带：

```text
--confirm-user-approved-sources
```

它表示用户已经看过并确认 `from_ids` 与直接表达形成说明。候选记录该确认事实；它不进入卡片正文。

### 3. 候选门禁

`permanent propose --type permanent` 必须同时满足：

- `from_ids` 非空，或者提供了有实际意义的 `--direct-source-file`；
- 用户已确认全部形成来源；
- 每个既有来源端点真实存在；
- 完整草稿已按现行作者权规则得到用户确认。

`source_ids` 非空不能单独通过形成来源门禁。

普通永久卡片专属参数如果传给 `mother`、`action` 或 `index`，CLI 必须明确拒绝，不能静默保存或忽略。

### 4. 正式接纳门禁与原子事务

`permanent accept` 必须重新检查：

- 候选仍为 `pending`；
- 草稿和直接形成说明的哈希一致；
- 来源确认事实存在；
- 所有 `from_ids` 端点仍存在；
- 最终 `derived_from` 至少有一个可寻址端点；
- 用户在候选创建以后明确要求正式创建。

通过后，在同一个现有原子事务中：

- 必要时创建最小来源见证；
- 创建普通永久卡片；
- 写入卡片到形成来源的 `derived_from` 关系；
- 在来源见证中写入指向正式卡片的反向关系；
- 把用户确认的形成说明原文机械包装为链接，呈现在系统维护的“形成来源”区域；
- 按状态边界处理作为形成来源的闪念；
- 删除待处理候选；
- 更新索引、日志和状态账本并生成聚焦 Git 提交。

任一检查或写入失败时，卡片、见证、闪念、候选、索引和账本全部保持原状。

### 5. 闪念状态边界

只有明确进入 `derived_from` 的闪念才参与状态转换：

- `pending → processed`；
- 已经是 `processed` 时保持原状态和原时间；
- `dismissed` 时拒绝接纳，不自动恢复；
- 以后如需恢复 dismissed 闪念，另行定义显式流程，本次不扩展。

### 6. Lint 与 Verify

只针对普通永久卡片新增检查：

- `derived_from` 非空；
- 每个端点存在且类型合法；
- 来源见证具有稳定 ID、有效形成说明、草稿哈希和反向关系；
- 卡片与来源见证双向一致；
- “形成来源”区域只包含用户确认的形成说明和 CLI 生成的导航链接，不混入 Agent 新写的认知正文；
- `source_ids` 只承担外部依据，不能代替 `derived_from`；
- 待处理普通永久卡片候选保留来源确认和必要哈希；
- 旧候选缺少新确认事实时不得被自动补为已确认。

其他三类永久卡片不应用这些条件检查。

## 五、Skill 调整

### `goodidea-form-permanent`

只为普通永久卡片增加：

1. 按节点内容标准审查；
2. 区分形成来源和外部依据；
3. 有既有材料时展示 `from_ids` 对象及形成作用；
4. 直接口述时，只整理一条用户已经表达并确认的形成说明，不保存完整聊天；
5. 用户确认全文和形成来源后调用 `propose`；
6. 报告已形成候选并等待新的正式创建指令；
7. 只有收到候选创建后的明确指令才调用 `accept`；
8. 不替用户补观点、理由、边界、形成情境或来源。

母题、行动和索引卡片保留现行审查逻辑。

### `goodidea-connect-cards`

- 删除“零连接也完成入网”的旧表述；
- 明确普通永久卡片在接纳时已经通过 `derived_from` 完成最低网络激活；
- 本 Skill 只负责接纳后的进一步语义连接；
- 没有额外语义关系时可以正常结束，不为丰富网络而造边。

## 七、兼容与迁移

当前正式普通永久卡片已经具有闪念 `derived_from`，符合新门禁，不需要修改正文或补建来源见证。

实施前只读检查两类对象：

- 现有正式普通永久卡片；
- 现有待处理普通永久卡片候选。

迁移规则：

- 不批量重写现有卡片正文；
- 不为历史内容补造来源见证、形成说明或用户确认；
- 旧候选缺少新确认事实时保持待处理，要求用户重新确认或撤销；
- 非破坏性回滚恢复旧候选时遵守同一规则；
- 母题、行动和索引卡片不迁移。

## 八、测试与验收

### 定向行为测试

至少覆盖：

1. 没有 `from_ids` 和直接形成说明时，普通永久卡片候选被拒绝；
2. 只有 `source_ids` 时不能通过形成门禁；
3. 外部来源同时作为依据和形成来源时可以进入两个字段；
4. 闪念、来源和其他已有认知材料可以作为 `derived_from` 端点；
5. 直接口述会在接纳事务中创建一个最小来源见证和双向关系；
6. 空洞形成说明、纯确认文本和未确认来源被拒绝；
7. `propose` 后没有新的正式创建指令时不能 `accept`；
8. `from_ids` 对象在候选后消失时，接纳失败且不留下部分状态；
9. 闪念只允许 `pending → processed`，不会复活 `dismissed` 或刷新已处理闪念；
10. 见证、卡片、闪念、候选、索引和账本保持事务原子性；
11. `accept` 后执行非破坏性 rollback，可以一致恢复卡片、见证和候选；
12. rollback 恢复的旧候选不会被误判为已确认；
13. 普通卡片专属参数传给其他三类时被明确拒绝；
14. 当前正式普通永久卡片继续通过 Lint；
15. 接纳后仍可独立建立进一步语义连接；
16. 正式卡片的用户认知正文与确认草稿一致，新增内容仅限确认过的形成说明和 CLI 机械导航包装。

### 项目检查

由于本次涉及跨层契约、核心事务、状态门禁、CLI 公共行为和 Skills，实施后运行：

```text
相关定向单元测试
uv run python -m unittest discover -s tests -v
uv run python scripts/validate-skills.py
uv run python scripts/evaluate-skill-routing.py
git diff --check
goodidea lint
goodidea verify
```

工作区如果存在本任务外未提交修改，Git 清洁问题单独报告，不清除或带入提交。

### 通过判据

- 无形成来源或无真实连接的普通永久卡片无法接纳；
- 形成来源和外部依据不会被机械混淆；
- 直接口述不需要人为补建闪念，不保存完整聊天原文，但具有一个有意义、可寻址的来源端点；
- 用户全文确认、来源确认和候选后的正式创建指令均不可绕过；
- 卡片、来源见证、形成关系和闪念状态保持原子一致；
- 历史候选和回滚不会伪造用户确认；
- 其他三类永久卡片没有被提前重构；
- 权威文档、Skills、实现和测试一致。

## 十、明确不做

- 不保存完整聊天原文；
- 不人为创建闪念；
- 不新增内容卡片类型；
- 不给来源见证增加 Review、生命周期或维护队列；
- 不把后续语义连接并入接纳事务；
- 不定义母题、行动和索引卡片的最终标准；
- 不实现任务调用闭环、关系本体、复杂检索、派生视图、认知 Review 或评分体系；
- 不为历史内容自动补造来源和关系。

## 十一、实施结果

本方案已经按确认边界落地。实现没有引入新的内容空间，没有保存完整原始对话，也没有改变母题、行动和索引卡片的准入契约。直接表达形成见证只存在于内部目录，并与卡片、候选、闪念状态、索引、日志和账本处于同一可回滚事务。
