# Good Idea 响应性能优化方案

日期：2026 年 9 月 26 日

## 一、优化目标

不是单纯把某个工具跑快，而是改变：

```text
松海发送一句话
→ Agent 反复探索、调用工具、重放历史、再次思考
→ 最后回复
```

改成：

```text
松海发送一句话
→ 本地快速接收与整理当前状态
→ 模型只做必要判断
→ 代码批量执行确定性动作
→ 返回骨架或最终结果
```

### 目标指标

| 指标 | 当前状态 | 第一阶段目标 |
|---|---:|---:|
| 首个可见反馈 | 随模型首轮返回 | 本地即时反馈，≤1 秒 |
| 普通捕捉续接 | 20～380 秒 | 常态 5～15 秒 |
| 服务侧降速时 | 可能数分钟 | 尽量控制在 60 秒内 |
| 捕捉类模型调用 | 7 次左右 | 通常 1～2 次 |
| 单轮输入 | 20k～150k+ token | 常态 ≤10k token |
| 机械操作模型调用 | 不确定 | 0 次 |
| 完整原始记录 | 保留 | 继续完整保留 |
| 用户判断权 | 保留 | 不改变 |

其中“≤2 次模型调用”应作为**捕捉续接等具体场景的预算**，不应成为所有复杂任务的全局硬规则。

# 二、第一性原理判断

## 1. 总耗时由串行决策链决定

可以把一次响应写成：

```text
T = Σ 模型决策时间
  + Σ 上下文重放时间
  + Σ 工具执行时间
  + 落盘与网关时间
```

当前实际数据表明：

- 模型时间约占 96%；
- 工具动作约占 4%；
- 第 3～5 次模型调用占模型总时间约 94%；
- 工具本身大多只有 0.1～0.4 秒。

因此优化重点不是：

```text
把文件读取从 0.2 秒优化到 0.1 秒
```

而是：

```text
不要为了读取文件，让模型多做三次判断。
```

## 2. 真正的问题不是“模型慢”，而是模型在控制所有事情

当前模型同时承担：

- 判断松海意图；
- 决定读什么；
- 搜索目录；
- 选择下一份文件；
- 决定是否写入；
- 决定如何验证；
- 决定是否提交；
- 组织最终回复。

其中只有第一项和最后一项主要需要模型。

其余大量动作属于确定性流程，本应由：

- 固定脚本；
- 本地 Hook；
- 批量执行器；
- 状态读取器；

完成。

当前系统的结构更接近：

```text
LLM 作为大脑
+
LLM 作为调度器
+
LLM 作为文件管理员
+
LLM 作为事务提交器
```

这会让每个低层动作都进入模型同步回路。

## 3. 完整对话不等于当前状态

完整原始记录的价值是：

- 保护思考过程；
- 让松海未来回看；
- 保留历史追溯；
- 支撑闪念形成。

但模型下一轮真正需要的通常只是：

- 当前正在判断什么；
- 已确认什么；
- 哪些问题还没定；
- 下一步是什么；
- 相关文件和材料在哪里。

如果每次都把完整历史当作工作状态，成本必然随会话增长。

所以需要把两者分开：

```text
完整记录 = 历史事实
当前状态 = 机器工作缓存
```

这不是删除过程，也不是增加一种新的产品对象。

# 三、总体架构

建议把运行链路拆成五层。

```text
① 事件接收层
② 上下文编译层
③ 模型判断层
④ 确定性执行层
⑤ 记录与后台层
```

## ① 事件接收层：本地立即处理

用户消息到达时，本地运行时直接完成：

- 接收消息；
- 写入当前会话；
- 判断是否存在明确的捕捉入口；
- 发送本地反馈；
- 建立本轮任务上下文。

这里不调用模型。

例如，首字反馈不应该让模型生成：

> “收到，我现在开始处理。”

而应该由网关或本地运行时直接显示：

> 已收到，正在整理当前状态。

这样降低的是感知时延，同时不会增加一次模型调用。

## ② 上下文编译层：prepare 包

新增本地上下文编译器，把本轮所需材料组装成一个固定小包。

建议入口：

```bash
python3 ~/.hermes/scripts/goodidea_prepare.py \
  --scene capture \
  --topic "认知卸载"
```

输出控制在约 5KB，包含：

```text
[当前场景]
[本轮目标]
[必要规则节]
[当前状态]
[材料结构]
[少量相关历史]
[文件路径指针]
[时间戳]
```

它不读取完整材料正文，除非明确要求。

prepare 包的作用不是替模型判断，而是提前完成：

```text
“到底应该把哪些东西交给模型看”
```

从而去掉：

```text
读技能
→ 再读规则
→ 再搜记录
→ 再读材料
→ 再决定下一步
```

这些探索轮。

## ③ 模型判断层：只做语义工作

模型第一次调用只做两件事：

1. 处理当前认知问题；
2. 给出结构化的执行意图。

例如：

```json
{
  "response_skeleton": {
    "judgment": "...",
    "mechanism": "...",
    "evidence": ["..."]
  },
  "actions": [
    {
      "type": "append_visible_messages",
      "target": "当前原始思考记录"
    },
    {
      "type": "update_state",
      "target": "当前状态"
    }
  ],
  "needs_followup": false
}
```

重要的是：

- 模型不逐个决定“先读哪个文件”；
- 模型不重复生成工具命令；
- 模型不为了落盘再调用一轮；
- 模型不把所有施工过程写成长文。

## ④ 确定性执行层：一次批量完成

代码根据结构化动作执行：

```text
并行读取
批量写入
更新状态
运行校验
生成报告
```

相互独立的操作应并行执行；有依赖关系的操作才串行。

执行完成后：

- 如果执行结果不会改变判断，直接返回第一次生成的骨架；
- 如果执行结果会改变判断，才进行第二次模型调用。

目标流程：

```text
第 1 次模型调用：判断 + 生成执行计划
        ↓
本地批量执行
        ↓
结果不影响判断：直接返回
结果影响判断：第 2 次模型调用收束
```

## ⑤ 记录与后台层：不阻塞前台

以下动作不能阻塞松海当前响应：

- Git 提交；
- Skill 使用复盘；
- 统计；
- 后台索引；
- 体检；
- 批量同步；
- 其他机器施工。

前台只保留：

```text
当前判断
当前回复
必要的记录确认
```

后台完成：

```text
完整落盘
状态页更新
Git 提交
统计
复盘
```

但要区分：

- **写文件成功**可以作为本轮完成条件；
- **Git 提交**可以放到后台；
- 不能在文件还没写成功时就声称记录已保存。

# 四、具体改造内容

## 改造 1：建立当前状态页

### 位置建议

放在原始思考记录的开头：

```markdown
## 当前状态

- 正在形成的判断：
- 已确认：
- 待决定：
- 下一步：
- 相关材料：
- 相关文件：
```

完整对话继续保留在下面。

### 约束

- 控制在 1～2k token；
- 只保存事实、当前判断和指针；
- 不保存完整推理过程；
- 不制造新的对象身份；
- 只在阶段结束或状态发生变化时更新；
- 下次优先读这一节，不默认重读全文。

### 为什么不单独建一种新对象

因为它不是闪念、永久卡片、行动或外部来源。

它只是原始思考记录的机器可读索引。把它做成新的正式对象，反而会引入：

- 对象身份问题；
- 同步问题；
- 召回问题；
- 第二套状态规则。

---

## 改造 2：建立场景化 prepare 编译器

第一版只支持少数真实场景：

```text
capture       捕捉与续接
distill       闪念辨析与永久卡片
source_sync   外部来源同步
discussion    普通项目讨论
```

每个场景定义固定读取清单，而不是让模型自行探索目录。

例如 `capture`：

```text
必须读取：
- 系统宪法相关节
- 内容对象中的原始思考记录节
- 捕捉协议
- 当前记录的当前状态
- 用户明确带入的材料结构

按需读取：
- 完整历史记录
- 外部材料正文
- 既有闪念卡片
- 行动记录
```

prepare 脚本只负责：

- 读取；
- 摘取；
- 拼装；
- 限制大小；
- 输出路径和摘要。

它不负责：

- 判断价值；
- 认领闪念；
- 替松海做决定；
- 修改产品规则。

---

## 改造 3：把消息落盘从模型回路中拿掉

当前捕捉协议要求：

1. 立即建立或续接原始思考记录；
2. 先保存触发消息；
3. 全部可见消息按顺序保存。

这类动作不需要模型判断，应该由运行时事件直接触发：

```text
用户消息进入
→ 立即追加用户消息

Agent 回复完成
→ 自动追加 Agent 消息

阶段结束
→ 更新当前状态
```

这能消除一个典型链路：

```text
模型决定写入
→ 调用写文件
→ 模型看到写入结果
→ 再生成确认
```

变为：

```text
事件发生
→ 本地写入
```

同时不会损害“完整现场保存”的规则，反而更符合现有捕捉协议。

---

## 改造 4：从低层工具切换到任务级工具

不要只给模型：

```text
read_file
search_files
write_file
terminal
```

还应提供任务级的本地编排入口，例如：

```text
goodidea_prepare
goodidea_append_messages
goodidea_update_state
goodidea_validate_record
goodidea_batch_sync
```

低层工具仍然保留，用于异常处理和复杂任务；正常路径优先走任务级工具。

区别是：

```text
低层工具：
模型自己编排 5～10 个动作

任务级工具：
代码内部完成 5～10 个动作，模型只收到一个结果
```

这一步才是真正把“往返次数”降下来。

---

## 改造 5：输出改为默认骨架

默认输出结构固定为：

```text
判断
机制
证据指针
```

例如：

```markdown
## 判断

核心问题不是工具慢，而是模型被放在了每个机械动作的同步回路里。

## 机制

当前流程把“判断、取料、写入、验证”拆成多个模型回合；
优化后改为“模型判断一次、代码批量执行、必要时再收束”。

## 证据

- 当前会话 7 次模型调用
- 模型耗时 366.5 秒
- 本地工具约 14 秒
- 第 3～5 次调用占模型耗时约 94%
```

默认不自动生成：

- 长篇过程复述；
- 已经讲过的背景；
- 每个工具动作的说明；
- 完整材料搬运；
- 没有改变判断的细节。

细节通过明确请求展开。

---

## 改造 6：建立调用预算，而不是只写原则

每轮开始时，运行时应该有一个预算对象：

```text
scene: capture
max_model_calls: 2
max_context_tokens: 10000
max_output_tokens: ...
allow_full_history: false
allow_background_work: false
```

超预算时不能默默继续。

应当：

1. 记录超预算原因；
2. 降级为当前骨架；
3. 或提示需要进入深度模式；
4. 不让普通任务无限探索。

预算不是为了压缩认知，而是为了防止机械动作无限占用模型回路。

# 五、按场景定义目标流程

## 场景 A：捕捉续接

```text
用户消息到达
→ 本地追加用户消息
→ 读取当前状态页
→ prepare 组装上下文包
→ 模型做一次判断并生成回应
→ 本地追加 Agent 消息
→ 更新状态页
→ 后台提交 Git
```

目标：

- 通常 1 次模型调用；
- 只有需要执行结果时才第 2 次；
- 不重读整场历史；
- 不因记录落盘再加一次调用。

## 场景 B：来源同步

```text
用户指定材料
→ 脚本直接取料、去重、落盘、图片处理
→ 模型只阅读报告
→ 返回同步结果
```

目标：

- 机械同步 0 次模型调用；
- 需要解释报告时 1 次；
- 正文和逐字稿不进入模型上下文。

现有 `goodidea-source-sync` 已经接近这个方向，应把它作为其他场景的范式。

## 场景 C：普通项目讨论

```text
读取状态页与指定材料
→ 模型一次分析
→ 不自动写文件
→ 只有松海明确要求才进入施工流程
```

目标：

- 讨论和施工分离；
- 普通讨论不因为模型顺手执行项目维护而变慢；
- 不把工具过程污染到认知上下文。

## 场景 D：复杂辨析

```text
读取闪念与必要形成依据
→ 模型提出一个关键判断
→ 松海决定
→ 必要时再形成候选
→ 松海认领后才写入正式对象
```

目标不是强行两轮，而是保证每一轮都在推进真实判断。

复杂辨析允许多轮，但不允许出现：

```text
读一份无关文件
→ 再搜索一个目录
→ 再重新解释已确认内容
```

# 六、实施阶段

## Phase 0：测量基线

不改变产品行为，先建立统一测量。

记录：

- 一轮模型调用数；
- 每次调用的输入、输出和延迟；
- 调用类型；
- 工具类型；
- 是否触发压缩；
- 缓存命中；
- 是否属于用户响应关键路径；
- 首字时间；
- 首个有用骨架时间；
- 完整响应时间。

需要新增或完善：

```text
~/.hermes/scripts/turn_timing.py
```

输出按轮聚合，而不是只按 API 调用罗列。

## Phase 1：先做机械路径

不改产品规则，先实现：

1. prepare 脚本；
2. 场景化读取清单；
3. 批量工具执行；
4. 消息自动落盘；
5. Git 后台提交；
6. 本地即时反馈；
7. 后台工作不阻塞前台。

这是收益最高、语义风险最低的一阶段。

## Phase 2：加入状态页

在原始思考记录中加入当前状态节。

同步更新：

- `规则/内容对象.md`
- `数据/模板/original-thought.md`
- 捕捉脚本或运行时更新器

注意：状态页内容应是事实与指针，不能成为新的分析文本。

## Phase 3：调整 Skill 编排

把现有 Skill 中的原则句改成可执行检查清单：

```text
本场景是否先读状态页？
是否读了完整材料？
若读了，是否有明确理由？
是否把独立操作合并？
是否把机械操作交给脚本？
是否在预算内？
是否把后台动作放到关键路径之外？
```

Skill 负责路由和约束；真正的性能门禁由脚本和运行时执行。

## Phase 4：再固化为规则

只有在多个真实场景重复验证后，才修改：

- `规则/协作协议.md`：执行顺序；
- `规则/默认规则.md`：输出预算、展开方式；
- `规则/内容对象.md`：当前状态的对象归属和更新方式；
- `规则/规则决策记录.md`：记录为什么固化。

`规则/系统宪法.md` 不需要修改。响应速度属于效率和编排问题，不触及当前硬边界。

# 七、验收标准

## 性能验收

至少验证以下场景：

| 场景 | 调用目标 | 输入目标 | 常态耗时目标 |
|---|---:|---:|---:|
| 捕捉续接 | ≤2 | ≤10k token | ≤15 秒 |
| 普通讨论跟进 | ≤2 | ≤10k token | ≤15 秒 |
| 来源同步 | 0～1 | ≤5k token | 取决于脚本，不受长正文影响 |
| 长会话第 10 轮 | 与第 1 轮同量级 | 不随全文增长 | 不出现线性恶化 |

## 正确性验收

- 完整原始思考记录没有丢失；
- 用户消息和 Agent 可见回复顺序正确；
- 未认领候选没有自动转正；
- 外部材料不会冒充用户判断；
- 状态页只保存事实与指针；
- 规则没有被 Skill 或脚本复制成第二套；
- prepare 失败时仍能继续当前对话；
- 后台任务失败不阻塞用户响应；
- 写文件真实完成后才报告已保存。

## 回归验收

特别测试：

- prepare 包读取失败；
- 状态页不存在；
- 原始记录格式异常；
- 同一消息重复到达；
- Git 提交失败；
- 长材料超过预算；
- 模型多次重复调用工具；
- 工具执行结果改变原判断；
- 用户说“只记录”；
- 用户中途取消或切换话题。

# 八、最终方案浓缩成一句话

```text
把 Good Idea 从“模型驱动的文件操作流程”，改成“状态驱动的认知协作流程”：
本地接收和记录，脚本编译上下文，模型只做判断，代码批量施工，必要时再让模型收束。
```

最优先的三个改动是：

1. **prepare 包：不再让模型自己探索上下文；**
2. **自动落盘：记录动作不再占用模型回合；**
