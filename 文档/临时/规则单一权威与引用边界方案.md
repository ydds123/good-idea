# 规则单一权威与引用边界方案

> 文档性质：临时方案与实施记录。松海已于 2026-09-26 确认方向并允许执行。
>
> 本文解释重构依据，不承担现行规则权威；实际行为仍以 `规则/` 中的归属文件为准。

## 一、要解决的问题

当前同一条语义会同时出现在系统宪法、对象契约、协作协议、默认规则、Skill、产品定义、模板和验证材料中。这样做短期容易读，长期会产生三个问题：

1. 同一概念可能出现多个“出口”，不同文件给出不同说法；
2. 规则调整时需要人工记住并修改多处，容易漏改；
3. 后来的读者无法判断某段文字是现行规则、执行说明、示例，还是历史记录。

根因不是文件多，而是**规范性语句没有唯一归属**。只要一条语义存在多个可以独立作出裁决的地方，系统就会出现多份潜在规则。

## 二、现状核查

当前项目已经在 `规则/README.md`、根 `README.md` 和 `AGENTS.md` 中声明“规则层是唯一权威”，说明方向本身已经存在；但它还不是系统宪法中的硬边界，也没有转化为可执行的写作约束。

实际重复主要集中在两类地方：

- 闪念卡片和行动的状态值域、转换条件与召回后果，同时出现在 `规则/内容对象.md`、`规则/协作协议.md`、`数据/README.md`、Skill、产品定义和验证材料中；
- Skill、模板和验证文件虽然声明“以规则为准”，正文仍重新描述了完整规则，因而仍可能独立漂移。

因此，现状不是“没有唯一权威声明”，而是**已经声明了唯一权威，但没有约束非权威文件只能引用什么、可以解释到什么程度**。

## 三、第一性原理

### 1. 一个判断只能有一个规范来源

系统需要回答的不是“哪份文件写得更详细”，而是“哪份文件有权决定这件事”。因此，每一项规范性定义必须有且只有一个**规范归属文件**（canonical owner）。

例如：

- “闪念卡片有哪些状态、状态意味着什么”属于对象契约；
- “辨析时先做什么、何时写入”属于协作协议；
- “相关性不足时默认不召回”属于默认规则；
- “为什么曾经这样设计”属于决策记录。

这些文件可以互相引用，但不能互相代替。

### 2. 宪法规定组织原则，不吞并所有细节

不建议把所有对象、状态和流程都塞进 `规则/系统宪法.md`。那会把一个重复问题变成一个过重的中心文件，最终形成“宪法既讲边界、又讲字段、又讲流程”的新混乱。

更稳妥的做法是：

- `系统宪法.md` 只规定“规则必须单一归属、其他文件只能引用”的元规则，并规定冲突处理方式；
- 每类语义仍由现有职责文件分别承载；
- `规则/README.md` 只做职责地图和阅读入口，不成为第二份产品规则。

也就是说，系统需要的是**一个单一权威体系**，不是一个承载所有内容的单一大文件。

### 3. 引用可以重复，定义不能重复

为了让文件可读，其他文件仍然可以出现状态名、对象名或流程名，但必须区分三种文字：

| 类型 | 允许出现的位置 | 处理方式 |
|---|---|---|
| 规范定义 | 规范归属文件 | 直接规定含义、范围、条件和后果 |
| 规范引用 | 非归属文件 | 明确链接到归属文件，不重新列出完整语义 |
| 示例或测试数据 | 模板、验证、试运行 | 可以出现具体值，但标明是示例、断言或场景输入，不产生新规则 |

因此，“模板里出现 `status: "待辨析"`”不一定是重复定义；如果模板只是展示格式，就是示例。如果模板再次解释四种状态和转换后果，就变成了第二套规则。

## 四、建议的规范归属矩阵

| 规则问题 | 唯一归属文件 | 其他文件的写法 |
|---|---|---|
| 不可绕开的边界、作者权、最终决定权、规则归属原则 | `规则/系统宪法.md` | 只引用，不再改写硬边界 |
| 对象是什么、不是什么、固定字段、状态值域、状态含义、转换条件、状态后果、形成依据 | `规则/内容对象.md` | 协议引用对象契约；模板提供最小示例 |
| 捕捉、辨析、行动登记、召回、来源登记的执行顺序 | `规则/协作协议.md` | Skill 只负责路由和加载；验证只验证流程 |
| 可调默认、召回偏好、提问启发式 | `规则/默认规则.md` | 其他文件不把启发式写成硬规则 |
| 规则为什么改变、何时生效、历史决策 | `规则/规则决策记录.md` | 不复制现行规则，只链接当前归属文件 |
| 数据目录、模板最小结构和 Markdown 表达方式 | `数据/README.md`、`数据/模板/` | 只表现数据形态；对象语义链接回 `规则/内容对象.md` |
| Skill 触发、排除、加载、停止和交接 | `.agents/skills/*/SKILL.md` | 不重新规定对象身份和状态含义 |
| 场景、路由、试运行和验收证据 | `验证/` | 只引用规则，允许使用测试值，不创造规则 |
| 产品背景、设计解释、历史方案 | `文档/` | 明确“以规则层为准”，不承担运行时裁决 |

其中，`规则/内容对象.md` 是对象语义的主要归属点；它不是所有规则的总文件。

## 五、拟加入系统宪法的原则

建议在 `规则/系统宪法.md` 增加一条元规则：

> **规范必须单一归属**：每一项规范性定义必须有且只有一个规则归属文件。归属文件负责给出该定义的含义、范围、条件和后果；其他文件只能通过明确引用、执行说明或验证示例使用它，不得复制、改写或扩展为另一套规则。出现冲突时，以归属文件和本宪法规定的规则层级为准。

同时在 `规则/README.md` 补充三点：

1. “文件职责”表就是规范归属索引；
2. 一段文字如果回答“应该是什么、何时成立、违反后果是什么”，就是规范定义，必须回到归属文件；
3. 其他文件只能写“如何调用、如何呈现、如何验证”，并链接归属章节。

这条原则的重点不是禁止关键词重复，而是禁止**同一问题存在多个裁决点**。

## 六、以闪念状态为例的重构方式

### 规范归属

`规则/内容对象.md#闪念卡片` 唯一负责：

- `status` 必须存在；
- 四个合法值；
- 每个值的含义；
- 哪些状态可以互转；
- `## 去向` 和永久卡片链接的条件；
- 时间不能自动改变状态。

### 协议引用

`规则/协作协议.md#闪念卡片辨析协议` 不再完整复述四个状态的定义，而写成：

> 闪念卡片的状态、转换条件和去向要求以 [`内容对象.md#闪念卡片`](../../规则/内容对象.md#闪念卡片) 为准。本协议只规定辨析时先呈现现场、再由松海作决定，并在决定发生后按对象契约写入。

### 模板引用

`数据/模板/flash.md` 保留一个最小示例：

```yaml
status: "待辨析"
```

模板只说明这是新建默认值，并链接对象契约；不复制状态机全文。

### 验证引用

验证材料可以写：

> 验证闪念卡片是否满足 [`内容对象.md#闪念卡片`](../../规则/内容对象.md#闪念卡片) 的状态不变量。

测试场景中仍可以出现“更新为 `已放弃`”这样的具体值，因为它是测试输入或预期结果，而不是新的值域定义。

## 七、后续修改流程

以后调整一条规则时，固定按以下顺序：

1. 先判断它属于哪个语义问题；
2. 在规范归属矩阵中找到唯一归属文件；
3. 只在归属文件修改规范正文；
4. 搜索其他文件中的重复定义，改为链接、执行说明或测试示例；
5. 运行规则一致性检查，至少确认没有旧值域、旧路径或冲突表述；
6. 在规则决策记录中记录原因，但不复制新规则全文。

如果某条语义无法归入现有文件，先判断是否真的出现了新职责；只有职责稳定且反复出现时，才新增规则文件或规则章节。

## 八、验收标准

方案实施后应满足：

- 每个对象的身份、字段、状态和转换各有唯一规范归属；
- 协作协议、Skill、模板、验证和产品文档能够通过链接找到归属正文；
- 搜索同一术语时，重复出现不再意味着重复定义；
- 修改一条对象规则时，原则上只改一份规范正文，其他改动仅限引用、示例或测试预期；
- 冲突时可以沿“系统宪法 → 归属文件 → 执行协议/默认规则”的路径裁决；
- 规则 README 能让新读者在一次阅读内知道“去哪份文件找什么”。

## 九、暂不做的事

- 不立即把所有规则合并进系统宪法；
- 不为每一个关键词建立复杂索引、数据库或自动生成层；
- 不为了消灭所有重复词语而改写历史正文和松海原始表达。

## 十、实施状态

方案已按确认方向执行：系统宪法确立单一归属原则，规则 README 建立职责索引，规则层内部收敛对象定义与协作顺序，非权威文件改为引用、格式示例、执行编排或测试断言。实施没有改变既有对象、状态或协作结果。
