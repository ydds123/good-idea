# 规则层与执行层分离优化方案（交接文档）

- 日期：2026-09-26
- 提出：松海；方案起草与审查：Claude（本文件由它起草，执行完成后由它审查）
- 执行者须知：本文件自包含，不需要原讨论上下文。动手前读完第 2、3 节；每个阶段单独提交，**不 push**。
- 与既有临时文档的关系：本方案**取代** `响应性能优化实施任务.md` 与 `Good Idea 响应性能优化方案.md` 的执行范围。那两份中的状态页、prepare 编译器、结构化动作 JSON、预算对象、任务级工具集**本次都不做**（见第 8 节）。它们的实测证据仍然有效，可作背景参考。

## 0. 一句话目标

把规则层里**本该由运行时或代码完成的确定性动作**从模型手里拿走，让模型只做判断；同时把这些动作做成可选、可替换的执行能力，以后改产品行为主要改 Markdown，不改执行实现。

## 1. 问题诊断（为什么要改）

规则文本本身不大：捕捉场景要加载的全部文件约 1.3 万字符。慢不来自规则长度，而来自规则把机械动作写成了模型义务。每个机械动作都要占一次「模型决定 → 调工具 → 看结果」的往返，而单次往返的成本近似于模型输出量 ÷ 输出速度（实测约 200 tok/s）。

根源是 `规则/系统宪法.md` 末句「不预设机械执行层」：规则里没写交给代码的，默认全落到模型身上。同时系统在仓库外已经有了执行层（`~/.hermes/skills/goodidea/goodidea-source-sync/scripts/sync_source.py`，`规则/标签树.md` 里提到的「登记脚本」），但规则不承认它，形成了看不见的耦合。

规则里仍交给模型做的机械动作：

| 位置 | 条款 | 性质 | 改为 |
|---|---|---|---|
| `协作协议.md` 捕捉协议第 1–2 步 | 建立或续接记录，逐条保存可见消息 | 纯转录；模型把回复再输出一遍作为写文件参数，外加 1–2 次往返 | 回合后钩子 |
| `AGENTS.md` 版本管理 | 每次续接都提交 Git（2026-09-26 一场捕捉产生 6 次 `capture:` 提交） | 机械 | 捕捉结束时由脚本提交 |
| `内容对象.md` / `数据/README.md` | 日期＋标题命名、同名加后缀；读模板再写文件 | 机械（标题仍由模型给） | `工具/new.py` |
| `标签树.md` 第 7 条 | 标签校验与体检「由 Agent 顺手跑」 | 机械 | 脚本自动跑，只有告警进对话 |
| `默认规则.md` | 炒饭会识别阈值 | 确定性判别 | 脚本读取参数（仅当脚本里已有硬编码时处理，见阶段 4） |
| 两个 Skill 加载第 1–6 步、`AGENTS.md` 读取顺序 | 「只有涉及……才读取」式的条件加载，外加日常必读 `规则/README.md` | 编排写成了逐步判断，产生探索往返 | 每个场景一份固定清单，首轮一次读齐 |

必须继续由模型判断的：是否进入捕捉、「只记录」、何时问与问什么、候选起草、价值判断、对象身份、「明显同一份材料」、标签的语义匹配、标题。

## 2. 硬约束：执行层必须薄且可插拔（本方案成败的关键）

松海上一套系统的教训是代码太重、难改。以下约束违反任何一条，审查不通过：

1. **代码只搬运，不判断。** 脚本中的条件分支只能涉及文件是否存在、格式是否合法、调用是否出错，不能涉及对象身份、价值、状态转换等产品含义。需要产品含义的地方由模型通过参数传入。
2. **行为写在 Markdown，不写在代码里。** 场景预读清单写在 Skill；何时调用哪个脚本写在 Skill；产品规则写在 `规则/`。改行为 = 改 Markdown。
3. **不抽取、不编译。** 规则文件整份读，不做按节摘取或上下文拼装器。
4. **每个脚本单一职责、可删除。** 删掉任意一个脚本，Agent 能按 Skill 里写明的退路手工完成同样结果，只是慢一些。
5. **规模上限。** 只用 Python 标准库；除迁入的既有 `sync_source.py` 外，新脚本每个 ≤150 行；不建共享内部库（几行重复可以接受）；不建配置系统；路径以仓库根为基准。
6. **平台隔离。** 只有 `工具/hooks/` 下的适配器知道 Hermes 的数据格式；其他脚本只接收通用的命令行参数或 stdin JSON。换运行时只需重写适配器。
7. **失败不阻塞。** 脚本和钩子失败时写日志、返回非零退出码，不能阻塞或回滚松海当前的对话（宪法第 4 条）。
8. **规则层不写「怎么执行」，执行物不写「是什么」。** `工具/README.md` 只写脚本做什么、怎么调用、失败时的手工退路，不定义任何产品规则。
9. **执行能力是可选插件，不是产品前提。** 规则和数据不能依赖某个脚本、某个运行时或某个目录存在；删除执行实现后，Skill 必须仍能按规则完成同样的产品结果。
10. **依赖方向只能向下。** 规则不依赖 Skill、脚本或平台；Skill 只依赖产品规则和执行契约；通用脚本不依赖 Hermes；平台适配器只依赖通用执行契约。
11. **契约先于实现。** 先定义最小能力接口、输入输出、失败语义和幂等规则，再实现 `工具/` 中的默认版本；不得让现有脚本行为反过来成为产品规则。当前每项能力只有一个实现，契约就是默认脚本的命令行接口，写在 `工具/README.md` 中；不单独建契约文件，不写接口抽象层或插件注册机制。
12. **可替换不等于共享状态。** `.goodidea/` 中的 session 映射和日志都是可重建的运行时派生状态，不是认知事实；去重等正确性不得依赖它们（见「最小执行契约」）；执行层不得把内部 ID、事件状态或平台字段写入正式记录作为必要语义。

## 2A. 可插拔执行能力边界（新增补充）

本方案引入的不是一个新的产品层，而是一组可选的执行能力。各层职责固定如下：

| 层 | 负责什么 | 是否定义产品语义 |
|---|---|---|
| `规则/` | 对象身份、保存内容、进入条件、协作结果和手工完成标准 | 是 |
| `.agents/skills/` | 场景路由、调用时机、能力不可用时的退路 | 只做协作编排 |
| 执行契约（写在 `工具/README.md`） | 能力的最小命令、输入输出、错误和幂等语义 | 否 |
| `工具/` | 当前默认的通用脚本实现，含 `工具/README.md` | 否 |
| `工具/hooks/` | 将某一运行时的事件转换为通用执行契约 | 否 |
| `.goodidea/` | session 映射、日志、待处理状态等可重建状态 | 否 |

规则层不得出现 `工具/`、`capture.py`、Hermes、`.goodidea/` 或其他执行路径。Skill 应直接写出默认命令，避免模型为寻找调用方式多走探索往返；但必须同时写明不可用或失败时的手工退路，不得把某个脚本写成唯一必经路径。执行实现可以更换、禁用或删除，不能改变规则定义的数据身份和协作结果。

### 最小执行契约

捕捉能力的默认契约只保留以下操作，具体实现可以是脚本、进程或其他插件：

```text
start(session_id, title, resume_path?)
append(session_id, events)
stop(session_id)
status(session_id)
```

其中 `events` 是与平台无关的可见事件，必须包含 `speaker`、`time` 和 `text`；`turn_id` 可选，只用于日志排查，不写入正式记录。契约规定：

- **幂等以记录本身为准**：写入前与目标记录中已有的消息比对，「时间＋说话人＋原文」完全相同即视为重复、不再写入。去重因此不依赖 `.goodidea/` 中的任何状态，运行时状态删除后结果不变。代价是同一分钟内同一说话人发出完全相同原文的真实消息会被合并；试运行中若真的出现，再单独讨论。
- **恢复只有一种方式**：重放 `append`，由幂等保证不重复。只处理阶段 0 实测中实际出现的异常（重复、乱序或中断）；没有观察到的情况不预先实现。
- **报告**：成功退出码为 0，失败为非 0，原因写入 stderr 和 `.goodidea/tools.log`。契约不规定对象价值、标签语义、状态转换或何时进入捕捉，这些仍由模型依据规则判断。

### 热插拔验收

除功能和性能验收外，每项执行能力必须通过以下替换测试：

1. 禁用平台适配器：规则和 Skill 不变，Agent 能按手工退路完成同样结果。
2. 删除通用脚本：正式记录、模板和规则仍可直接读写，已有数据不失效。
3. 禁用 Git 提交能力：记录仍能写入；提交失败不阻塞对话，`status` 能显示未提交事实。
4. 替换为等价实现：只要遵守执行契约，正式记录内容和产品结果一致。本条在真的出现第二个实现时再验收，不为验收专门编写第二个实现。

未通过热插拔验收的实现，不得固化为默认能力，也不得要求修改规则层来迁就实现。

### 修改边界速查

后续维护先按变化类型定位层次，避免跨层修改：

| 要改的东西 | 默认只改哪里 | 不应顺带修改 |
|---|---|---|
| 对象身份、状态、进入条件、协作结果 | `规则/` | `工具/`、Hermes 适配器 |
| 何时尝试自动化、如何降级和补写 | 对应 Skill | 产品对象定义、脚本内部判断 |
| 事件字段、幂等、错误和恢复语义 | 执行契约及其说明 | Hermes 专有格式、产品规则 |
| 文件创建、追加、状态查询 | `工具/` 默认实现 | 规则正文、平台适配逻辑 |
| Hermes 事件读取和转换 | `工具/hooks/` | `capture.py`、规则和 Skill |
| Git 提交策略 | `工具/commit.py` 及适配器中对它的调用 | 捕捉记录格式、产品状态 |

如果一次需求需要同时修改两层以上，必须在阶段提交说明中写出跨层原因；不能因为默认实现方便，就把实现细节上移为规则。

## 5. 分阶段任务

执行顺序：阶段 0 与阶段 1、2 互不依赖，可以并行；阶段 3 必须等阶段 0 的结论；阶段 4 可以独立进行。

### 阶段 0 · 验证运行时事件契约（只读探针，不改产品规则）

阶段 3 依赖 Hermes 能提供可靠的回合事件。先做最小探针，确认以下事实后才能实现 Hermes 适配器：

- 能否取得最终对用户可见的 Agent 回复原文，而不是含工具调用、思考过程或系统内容的原始流；
- 能否取得本回合用户可见消息、稳定的 `session_id`、`turn_id` 或等价事件标识；
- 同一回合是否可能重复触发、乱序触发或在回复失败后再次触发；
- 钩子是同步还是异步，p95 执行时间是否满足回合后路径要求；
- stop 所在回合的最后一条用户消息和 Agent 回复，是否会在关闭前可靠到达。

探针只记录事件字段、时序和耗时，不写入正式记录，不改变规则或 Skill。若无法取得最终可见回复原文，暂停阶段 3，改用模型手工追加或其他可验证的事件来源，不把 Hermes 内部流格式写进产品规则。

验收：提交说明中列出上述结论、事件样例摘要、重复/乱序行为和耗时分位数；未完成这一步，不得声称捕捉转录已可自动化。

### 阶段 1 · 固定加载清单与输出骨架（只改 Markdown）

**1a. 两个 Skill 的「权威与加载」改为固定清单，首轮一次并行读齐。**

- `goodidea-capture` 首轮读取：`规则/系统宪法.md`、`规则/内容对象.md`、`规则/协作协议.md`、`规则/默认规则.md`（四份整读，合计约 8.3k 字符）。不再读取 `数据/README.md` 和模板（由阶段 2、3 的脚本处理）。
- `goodidea-distill` 首轮读取：同样四份，加上松海指向的目标卡片。形成依据等其他文件只在需要时读取。
- 召回、行动、来源材料仍然按需读，但写成「需要时在同一轮内一次读齐」，不再分多步。
- 措辞示意（执行者可调整，但必须保持「固定清单 + 一次读齐」）：

  ```markdown
  ## 加载
  首轮在同一次工具调用批次中读取以下文件，之后不重复读取已在上下文中的内容：
  - ../../../规则/系统宪法.md
  - ../../../规则/内容对象.md
  - ../../../规则/协作协议.md
  - ../../../规则/默认规则.md
  ```

**1b. `AGENTS.md` 拆分两条路径的读取顺序。**

- 产品使用（含不走 Skill 的有意思、行动、来源、召回）：一次读齐 `系统宪法.md`、`内容对象.md`、`协作协议.md`，需要时加上 `默认规则.md`。**不再必读 `规则/README.md`。**
- 仓库维护：保持现有顺序（先经 `规则/README.md` 定位归属）。
- 保留「本文件不定义产品规则」的定位。

**1c. `规则/默认规则.md` 的「Agent 启发式」增加输出骨架条目。**

内容要点：默认先给判断、机制和证据指针（文件、数字），细节按需展开；不复述已经确认的内容；不在回复里叙述工具过程。字数上限由松海裁决，未裁决前不写数字。捕捉中回应松海正在思考的内容时，骨架让位于对话本身。

**1d. 清理 Hermes 侧的重复副本。** 检查 `~/.hermes/skills/` 下是否存在 `goodidea-capture`、`goodidea-distill` 或其他 goodidea 技能的**独立副本**。若存在，改为指向仓库 `.agents/skills/` 的符号链接（或 Hermes 支持的等价方式），删除副本；否则仓库里的修改不会生效。在提交说明里列出处理结果。

验收：
- 在新会话中触发一次捕捉：首轮只有一个读取批次，没有第二轮探索读取。
- `grep -n "规则/README" AGENTS.md .agents/skills/*/SKILL.md` 只在仓库维护路径中出现。

### 阶段 2 · 承认可插拔执行能力 + `new.py`

**2a. 修改系统宪法**，末句改为以下意思（措辞可以调整，含义不可弱化），可作为第 9 条或放在末段。宪法只承认可选执行能力，不写具体脚本、目录或 Hermes：

> 确定性的搬运动作（转录、命名、校验、提交）可以交给可选的执行能力。执行能力不得承载产品判断；不可用或失败时不得阻塞当前表达；删除后规则和数据仍能独立成立，并能由 Agent 手工完成同样结果。

**2b. 同步引用。**
- 根 `README.md` 的「当前结构」加入 `工具/`，并说明它是可选的执行物，不是规则来源。
- `规则/` 下的文件不提及 `工具/` 或任何脚本（见第 2A 节）；宪法只写「可选的执行能力」。
- `AGENTS.md` 修改边界加一条：当前默认执行脚本放在 `工具/`，不得包含产品判断；平台相关代码只放 `工具/hooks/`。Skill 依赖执行契约，不把某个脚本路径写成唯一实现。
- `规则/规则决策记录.md`：新增一条，说明为什么引入薄执行层，并注明它部分取代 2026-09-25「移除机械层」（那条移除的是索引、ID、事件等机械状态；本次引入的是无状态的搬运脚本）。

**2c. `工具/new.py`**

```text
python3 工具/new.py <类型> "<标题>"   # 类型：interesting | action | flash | permanent | source
→ 从 数据/模板/ 复制对应模板到对应目录，文件名 YYYY-MM-DD-标题.md，同名追加 -2、-3
→ stdout 打印创建的路径
```

- 日期取本地当天。只负责「创建空壳」，内容由模型随后填写。
- 模板顶部的「对象语义以……为准」引用行是否保留在生成文件里，按现有正式记录的实际做法来（先查已有记录再定，不要自行发明）。
- 两个 Skill 和 `协作协议.md` 的有关写入步骤**不改规则措辞**；只在 Skill 编排里写「创建正式记录时调用 `工具/new.py`；脚本不可用时按 `数据/模板/` 与命名规则手工创建」。

验收：五种类型各创建一次，文件名、目录和模板内容正确；同名冲突产生 `-2`；删掉脚本后按 Skill 退路仍能手工完成。

### 阶段 3 · 捕捉转录交给可选能力与回合后适配器（收益最大）

**3a. `工具/capture.py`（通用，不知道 Hermes）**

```text
capture.py start  --session <id> --title "<标题>" [--resume <已有记录路径>]
    新建：用 new.py 的同一命名规则创建 数据/记录/闪念/原始思考记录/<文件>（模板：original-thought.md）
    续接：不新建文件；续接说明由模型写（属于判断）
    在 .goodidea/capture-sessions.json 登记 session → 记录路径
capture.py append --session <id>        # stdin：JSON 数组 [{"speaker":"松海|Agent","time":"YYYY-MM-DD HH:MM","text":"...","turn_id":"...(可选)"}]
    session 未登记 → 直接退出 0（不在捕捉中，什么都不做）
    按 "### YYYY-MM-DD HH:MM｜松海/Agent" 格式追加；文末已有 "## 去向" 时插在它之前
    按「时间＋说话人＋原文」与记录中已有消息比对去重（见第 2A 节最小执行契约）
capture.py stop   --session <id>
    标记 closing；仍接受 stop 所在回合已产生的事件；确认最后事件落盘后注销该 session。capture.py 自身不做 Git 提交；提交由适配器收尾时调用 commit.py 完成（见 3b）
capture.py status --session <id>
    打印：记录路径、已写入回合数、最近一次失败（如有）、是否有未提交改动
```

**3b. `工具/hooks/hermes_post_turn.py`（当前默认的 Hermes 适配器）**

- 从 Hermes 回合后钩子取得：session id、本回合用户消息、Agent **最终可见回复**、时间。
- 只传可见文本，过滤掉工具调用、思考过程和系统内容。
- 转成平台无关的事件 JSON，调用 `capture.py append`；若该 session 处于 closing，待最后事件确认落盘后执行收尾：注销 session，再调用 `工具/commit.py <记录路径>`（提交说明沿用 "capture: …" 风格）。只有适配器能在最后一条回复落盘之后触发提交，所以提交调用放在这里；删掉这一调用即禁用版本提交能力。提交失败只写日志，`capture.py status` 显示为「有未提交改动」。
- 失败时写 `.goodidea/tools.log`，退出非零，绝不阻塞回复显示。
- 在 Hermes 配置中注册该钩子；在 `工具/README.md` 写明注册位置和方式。

**3c. 执行者必须先核实的三件事（结论写进提交说明）**

1. 钩子能否拿到**最终可见回复原文**，而不是含工具调用的原始流。拿不到时停下，报告松海，不要猜；该结论应已由阶段 0 探针给出。
2. 钩子能否拿到本会话更早的消息。能的话，`start` 支持用 `--carry N` 带入确认前的 N 条可见消息（对应捕捉协议里「用户确认后可带入前序消息」）；不能的话，这种情况由模型手工调用 `capture.py append` 写入。
3. 钩子是同步还是异步。同步时必须确保执行时间足够短（目标 <300ms），否则改为后台执行。

**3d. 改 `goodidea-capture` 的编排（不改规则）**

- 进入捕捉：执行 `python3 工具/capture.py start ...`（默认命令直接写在 Skill 中），然后直接回应松海的内容。**此后每轮不再写文件、不再提交**；能力可用时由适配器转录，能力不可用或失败时按退路手工完成。
- 「只记录」或自然结束：执行 `python3 工具/capture.py stop ...`，并按协议回复；版本提交能力是否启用不影响记录关闭。
- 退路：钩子未安装或 `status` 显示失败时，Agent 用 `capture.py append` 手工补写；`capture.py` 也不可用时，按模板手工写文件。
- 删除现有 Skill 中所有「把可见对话保存到……」这类让模型亲自转录的措辞，但保留能力不可用时的手工退路。

**3e. `AGENTS.md` 版本管理补一句**：捕捉过程中不逐轮提交；捕捉结束后由适配器调用 `工具/commit.py` 统一提交目标记录。未启用该能力时，记录仍然有效，Skill 按退路提示或协助人工提交。

验收：
- 一次真实捕捉续接回合：模型调用 1 次（不含任何写文件、提交的工具调用）；异常时 ≤2 次。
- 回合输出 token 近似等于回复本身，不再出现同一段正文输出两遍。
- 常态端到端耗时 ≤15 秒（服务侧降速窗口除外）。
- 记录与实际可见对话逐条一致：顺序、时间、说话人、原文；不含工具内容。
- 回归：同一事件触发两次 → 不重复；中断后重放同一批事件 → 不重复、不遗漏；删除 `.goodidea/` 后重放 → 结果不变；阶段 0 实测出现乱序时 → 按实测方案处理；适配器被禁用 → Skill 退路能补齐；「只记录」→ 当轮消息写入后会话注销；Git 提交能力禁用或失败 → 不影响对话，`status` 可见；续接既有记录 → 追加到正确文件，插在 `## 去向` 之前。

### 阶段 4 · 来源登记与标签脚本迁入仓库

1. 把 `~/.hermes/skills/goodidea/goodidea-source-sync/scripts/sync_source.py` 迁入 `工具/`；Hermes 侧技能改为调用仓库路径，删除旧副本。**只迁移、修路径，不借机扩写功能。**
2. 标签校验和体检：若 `sync_source.py` 已包含这部分逻辑，就提供一个子命令（如 `sync_source.py tags-health`），不另拆文件；否则拆一个 ≤150 行的 `tags.py`。登记时自动校验；只有出现告警时才进入对话。
3. `规则/标签树.md` 第 7 条改为：校验与体检由登记脚本自动执行，**告警**由 Agent 在当次登记中就地处理。处理方式（改挂、先建后引、并入）是判断，保留原措辞。
4. 炒饭会阈值：检查脚本中是否硬编码了「周三 17:00 / 20 分钟 / 工作会议」。如果有，把数值移到 `规则/标签清单.json` 中「炒饭会」节点的一个新字段（如 `识别参数`），脚本从那里读；`默认规则.md` 那条改为引用该字段，不再重复写数字；决策记录注明。如果没有硬编码，不动。
5. 退场规则（6 个月、≤2 份、10 份提醒）：由体检输出**事实**（每个标签的份数、最近一次使用日期），不由脚本自动标注停用。停用仍需 Agent 提出、松海确认。

验收：来源登记一次，对话内模型调用 ≤2 次（调用脚本 + 汇报）；删除 `~/.hermes` 下的旧副本后功能正常；`grep` 确认阈值数字只出现在一处。

## 9. 交付与审查

每个阶段一个提交，提交说明包含：改了什么、第 3c 节等核实结论（如适用）、改前改后的测量数字、偏离本方案之处及原因。

审查时将逐项检查：

1. 脚本中是否出现产品判断分支（第 2 节第 1 条）。

12. 去重等正确性是否依赖 `.goodidea/` 中的状态。
