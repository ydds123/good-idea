# 旧数据语义迁移方案

> 文档性质：本文件是旧数据迁移的实施方案，不是已经生效的产品规则。实际迁移前，必须先按本方案修改 `规则/` 与 `数据/` 中的权威定义并完成验证。旧项目 `/Users/apple/Documents/good-idea` 在全过程中保持只读。

## 一、目标

将旧项目中的 `有意思空间/`、`永久空间/`、`闪念空间/` 及其必要依赖迁入当前项目，使迁移结果满足当前项目更新后的对象、状态、版本、形成依据、目录和文件格式要求。

这不是无序搬运，也不是禁止复制。迁移允许复制旧内容，但每一份复制都必须：

1. 有明确的目标对象身份；
2. 登记在迁移清单中；
3. 使用当前项目的数据格式、中文状态和文件命名；
4. 清理或转换旧系统专属字段；
5. 通过引用、图片、状态和内容完整性验证。

## 二、松海确认的迁移要求

1. 方案必须落盘后再实施。
2. 旧数据允许复制进新系统，但只能按迁移清单有条件地复制，不能整库无序倾倒。
3. 当前项目新增第五类正式内容对象：`有意思`。
4. 旧闪念中状态为“待处理”的记录，迁移后继续标识为 `待处理`；当前状态集合没有该状态时必须补充。
5. 正式数据中的状态枚举统一改为中文。
6. 旧项目的原始思考会话、捕捉会话和讨论日志不迁移。
7. 正式内容文件统一命名为 `日期-序号-标题名.md`，文件名前不带 `SES-`、`FLA-`、`INS-`、`SRC-` 等类型前缀。

## 四、迁移后的对象体系

迁移后，当前项目承认五类正式内容对象：

1. 原始思考会话；
2. 有意思；
3. 正式闪念；
4. 永久认识；
5. 外部来源。

原始思考会话仍用于当前项目未来发生的新捕捉，但旧项目中的历史会话不迁移。

### 4.1 有意思

“有意思”用于保存松海明确认为值得留下、未来可能使用或继续判断，但尚未认领为正式闪念、永久认识，也不要求立即建立完整来源快照的内容。

它可以是：

- 工具、网站、仓库、模型或产品；
- 可复用提示词、方法素材或案例；
- 一个值得回看的外部材料入口；
- 尚未形成清晰判断的参考方向。

它不等于：

- 外部来源快照；
- 松海已经认领的认知种子；
- 当前愿意接受并调用的永久判断。

最小内容包括：

- 保存的对象或内容；
- 当时为什么觉得有意思，已有则保留，没有则不补写；
- 原始链接或材料入口，已有则保留；
- 后续处理结果，实际发生后再记录。

状态集合：

| 状态 | 含义 |
|---|---|
| `待处理` | 已保存，尚未决定是否进一步处理 |
| `已处理` | 已有明确处理结果，可指向来源、闪念、永久认识或其他实际结果 |
| `已放弃` | 当前不再值得继续占用注意力，历史仍保留 |

正式目录：`数据/记录/有意思/`。

模板：`数据/模板/interesting.md`。模板文件名属于机器约定，可以保持英文；正式记录文件名必须使用中文标题和统一日期格式。

## 五、中文状态契约

| 原状态 | 中文状态 |
|---|---|
| `recording` | `记录中` |
| `closed` | `已关闭` |

### 5.2 有意思

- `待处理`
- `已处理`
- `已放弃`

### 5.3 正式闪念

| 原状态 | 中文状态 |
|---|---|
| `pending` | `待处理` |
| `fermenting` | `发酵中` |
| `dismissed` | `已放弃` |
| `expired` | `已失效` |
| `formed` | `已形成认识` |

`待处理` 是正式、合法的闪念状态。旧待处理闪念迁移后继续保持 `待处理`，不因历史时间已经过去而自动改为 `已失效`。

历史迁入的待处理闪念不追溯执行 48 小时保鲜规则：迁移时允许 `window_ends_at` 留空；松海以后明确重新激活或开始辨析时，再建立新的保鲜窗口。该例外只适用于本次旧数据迁移，不改变新产生闪念的默认规则。

## 六、文件名与内部身份

### 6.1 文件命名

五类正式内容统一使用：

```text
YYYY-MM-DD-NNN-标题名.md
```

例如：

```text
2026-08-10-001-《无期迷途》游戏美术风格.md
2026-08-13-002-职业规划已失效：行业选择是长出来的.md
```

约束：

- 文件名前不得出现对象类型字符前缀；
- 日期使用对象真实创建、保存或认领日期；
- 序号按“对象目录＋日期”分别递增；
- 同日排序使用旧创建时间、旧 ID、旧路径作为确定性排序依据；
- 标题只做文件系统必要清理，不擅自改写松海的标题；
- 路径和标题可以变化，内部 ID 不随之变化。

### 6.2 内部 ID

`SES-*`、`INT-*`、`FLA-*`、`INS-*`、`SRC-*` 只作为 Markdown Frontmatter 中的稳定身份，不再出现在文件名开头。

旧 ID 与新 ID 的对应关系写入迁移清单，不用旧 ID 污染新文件名。

## 七、有条件复制规则

迁移按三种模式执行。

### 7.1 原内容复制

适用：

- 图片和附件二进制；
- 可以作为真实来源快照保留的原文；
- 不需要改写的用户正文段落。

要求：复制前后计算哈希，证明内容没有变化。

### 7.2 复制后结构转换

适用：

- 闪念正文；
- 永久认识正文；
- 有意思记录；
- 来源记录的身份和快照结构。

允许调整：

- Frontmatter；
- 标题层级；
- 章节顺序；
- ID、状态、路径和引用。

不得擅自调整：

- 松海的实际判断；
- 用户表达的必要理由；
- 真实边界、不确定性和演化内容；
- 外部来源的原文快照。

### 7.3 拆分或合并

只有对象身份确实混杂时才使用：

- 一条记录同时包含外部材料和松海自己的判断时，可以拆成来源与闪念；
- 多个旧来源明确属于同一规范身份时，可以合并为一个来源对象的多个引用或快照；
- 不因标题相似自动合并；
- 不因闪念与永久认识标题相同删除闪念，二者身份不同。

### 7.4 禁止的复制方式

- 不把三个旧目录整包复制到新目录；
- 不把旧 Frontmatter 原样带入；
- 不复制旧业务代码、Skill、状态机或运行时目录；
- 不把全部 83 个旧资产无差别复制；
- 不把旧项目的目录结构复制为新项目结构；
- 不在迁移清单之外创建正式文件。

## 八、旧原始思考会话处理

旧项目中的 `CAP-*`、`.goodidea/runtime/completed-captures/`、`discussion_log` 和其他历史会话数据不迁移。

处理规则：

- `capture_session`、`discussion_log` 从新 Frontmatter 中删除；
- 不创建对应 `SES-*`；
- 不把摘要、候选清单或直接表达见证伪造成完整会话；
- 旧闪念正文中已经存在的触发情境、激活逻辑和用户表达继续保留；
- 新项目以后发生的捕捉仍按原始思考会话规则保存，不受本次历史迁移影响。

对于唯一以旧 `WIT-*` 直接表达见证作为形成依据的永久卡《AI 时代的主要矛盾：生产不再需要人，人仍靠“被需要”而活》：

- 不把 `WIT-*` 转成会话；
- 保留卡片中已有的真实形成叙述；
- 在版本正文中增加“历史形成说明”，明确这是旧项目已确认的直接表达记录；
- 迁移清单保存旧见证 ID 和旧文件哈希；
- 该迁移例外不成为新项目未来创建永久认识的旁路入口。

## 九、各类旧数据的迁移规则

### 9.1 有意思空间

13 条旧有意思记录原则上迁移为新的 `有意思` 对象，状态统一保留为 `待处理`。

迁移时：

- 保留原始记录、产生情境和演化内容；
- 清理旧 `INT-*` 身份并生成新项目内部 ID；
- 已存在的链接和来源关系继续登记；
- 不因为内容指向网页就自动把整张记录改成外部来源；
- 松海以后明确处理时，再决定是否登记来源、形成闪念或形成永久认识。

若某条旧记录本身保存的是完整外部原文，可以同时建立来源快照；但“有意思”对象仍保留其独立身份和保存动机，不因来源登记而被吞掉。

正文转换：

| 旧章节 | 新章节或处理 |
|---|---|
| 原始记录／闪念内容 | 核心内容 |
| 产生情境／触发情境 | 触发情境 |
| 激活逻辑 | 保留为当时的推理，不删除 |
| 来源与论证锚点 | 转为材料引用或形成说明 |
| 演化记录 | 区分认知补充与状态变化后保留 |
| 连接 | 纯导航删除；含实际判断的文字保留为正文 |

### 9.3 永久空间

21 张旧永久卡都属于旧系统中已经由松海确认的正式内容，不退回候选。

| 旧状态 | 数量 | 迁移方式 |
|---|---:|---|
| 有效 | 17 | 状态 `有效`，建立 v1 |
| 已修订 | 4 | 状态 `有效`，从旧 Git 历史重建版本 |

四张已修订卡：

- 《主体性：行为原因的自我归属》；
- 《职业规划已失效：行业选择是长出来的》；
- 《判断力不靠熬年头，靠主动催化》；
- 《母题级课题：AI 图像／摄影与视觉叙事的 skill 化》。

版本重建要求：

- 优先使用旧 Git 历史恢复真实旧版本；
- 区分认识修订与普通过程备注；
- 不根据当前正文猜测旧版本；
- 长篇论证完整保留，不为了套模板压缩成摘要；
- “演化方向”“待探索问题”中属于松海实际认识的内容继续保留；
- 纯机器维护的连接导航不迁移。

形成依据优先转换为：

- 已迁移闪念；
- 已迁移来源的具体快照；
- 既有永久认识的具体版本；
- 本方案第八节定义的旧见证迁移例外。

### 9.4 外部来源与图片

只迁移被正式迁移对象实际引用的来源和图片。

来源处理：

1. 解析规范身份；
2. 检查重复身份；
3. 保留所有真实原始引用；
4. 将旧来源正文复制或转换为来源快照；
5. 根据实际完整程度使用中文状态；
6. 永久认识引用具体快照，不只引用抽象来源 ID。

建议新增：

```text
数据/资产/<sha256>.<扩展名>
```

图片处理：

- 只复制关系图中使用的 73 个文件；
- 复制前后校验 SHA-256；
- 相同内容只保留一份；
- Markdown 使用相对路径；
- 不保存旧项目绝对路径；
- 不因图片复制改变来源正文含义。

## 十、Frontmatter 清理

### 10.1 迁移后不再保留的旧字段

- `type`
- `title`
- `updated_at`
- `source_ids`
- `derived_from`
- `authoring_mode`
- `formation_draft_sha256`
- `capture_session`
- `discussion_log`

这些字段不是一律丢弃，而是按以下方式转换：

| 旧字段 | 新去向 |
|---|---|
| `title` | 文件名与一级标题 |
| `updated_at` | 状态历史或版本历史中的真实事件 |
| `source_ids` | 来源或具体快照引用 |
| `derived_from` | 形成依据 |
| `capture_session` | 删除，不迁旧会话 |
| `discussion_log` | 删除，不迁旧讨论日志 |
| 旧 `id` | 迁移映射表 |
| `formation_draft_sha256` | 迁移核验时使用，完成后不进入正式认知字段 |

### 10.2 新 ID

新项目继续在 Frontmatter 中保存稳定内部 ID，但不放进文件名。旧 ID 到新 ID 的映射由迁移清单保存。

## 十一、迁移清单

实际迁移前生成：

```text
数据/系统/操作事件/MIG-YYYYMMDD-NNN.json
```

每条旧记录至少包含：

```json
{
  "legacy_path": "旧相对路径",
  "legacy_id": "旧 ID",
  "legacy_sha256": "旧文件哈希",
  "copy_mode": "原内容复制 | 复制后结构转换 | 拆分或合并 | 暂缓",
  "target_type": "有意思 | 闪念 | 永久认识 | 外部来源",
  "target_id": "新内部 ID",
  "target_path": "新相对路径",
  "status_mapping": "旧状态 → 中文新状态",
  "removed_fields": [],
  "dependencies": [],
  "decision": "自动规则或松海裁决",
  "validation": "待验证或已通过"
}
```

要求：

- 63 份输入全部登记；
- 每份都有迁入、拆分、合并或暂缓结果；
- 一个旧对象拆成多个新对象时全部列出；
- 多个旧对象合并时保留全部来源路径和哈希；
- 不允许清单外写入。

## 十二、实施顺序

### 阶段 0：规则准备

修改并同步：

- `规则/系统宪法.md`：四类对象改为五类，加入有意思的作者权和身份边界；
- `规则/内容对象.md`：定义有意思和全部中文状态；
- `规则/协作协议.md`：补充有意思的保存与处理入口；
- `规则/默认规则.md`：调整中文状态和历史待处理迁移例外；
- `规则/规则决策记录.md`：记录本次迁移与对象扩展决定；
- `数据/README.md`：允许有条件复制，增加有意思和资产目录；
- `数据/模板/*.md`：状态改中文，新增 `interesting.md`，文件示例移除类型前缀；
- `README.md`、项目 Skill 和验证材料：只引用更新后的权威规则，不另建同义规则。

修改权威规则前按项目审批要求执行。

### 阶段 1：只读迁移清单

1. 固定旧项目读取版本；
2. 比较当前旧数据与冻结提交；
3. 计算 63 份内容、17 份来源和 73 个图片的哈希；
4. 建立旧 ID、路径、形成关系和资产关系图；
5. 生成完整迁移清单；
6. 不写入正式记录目录。

### 阶段 2：松海裁决歧义项

集中审阅：

- 3 条无永久认识去向的已处理闪念；
- 1 条已放弃但后来参与修订的闪念；
- 4 张已修订永久卡的版本边界；
- 可能发生来源合并或对象拆分的记录。

13 条旧有意思不再需要重新判断对象类型，默认迁为 `有意思／待处理`；只有松海明确要求继续处理时，才另外形成来源、闪念或永久认识。

### 阶段 3：迁移有意思

- 建立 `数据/记录/有意思/`；
- 迁移 13 条记录；
- 统一中文状态；
- 保留原始记录、产生情境、演化内容和实际链接；
- 验证不夹带旧 Frontmatter。

### 阶段 4：迁移来源和资产

- 迁移 17 份必要来源；
- 复制 73 个必要图片；
- 完成身份去重、快照编号、哈希验证和相对路径重写。

### 阶段 5：迁移闪念

- 迁移已能确定状态的记录；
- 应用松海对四条歧义记录的裁决；
- 建立中文状态历史；
- 不迁旧会话路径。

### 阶段 6：迁移永久认识

- 17 张建立 v1；
- 4 张重建多版本；
- 重建形成依据；
- 处理旧见证迁移例外；
- 删除纯机器连接导航，保留实际认知内容。

### 阶段 7：全量验收与提交

按对象类型分批验证和提交。任一批失败，只回退该批，不修改旧项目，也不清理已通过批次。默认不推送远程。

## 十三、验收标准

### 13.1 完整性

- 63 份旧输入全部出现在迁移清单；
- 17 份必要来源全部有结果；
- 73 个必要图片全部完成哈希核验；
- 没有静默丢失；
- 旧项目零改动。

### 13.2 对象和状态

- 正式对象只有五类；
- 所有正式状态均为中文；
- 6 条旧待处理闪念迁移后仍为 `待处理`；
- 13 条旧有意思迁移后为 `有意思／待处理`；
- `已修订` 不作为永久认识状态残留；
- 不创建历史原始思考会话。

### 13.3 文件和字段

- 所有正式内容文件符合 `YYYY-MM-DD-NNN-标题名.md`；
- 文件名前没有对象字符前缀；
- 内部 ID 稳定且唯一；
- 没有旧运行时路径、绝对路径或废弃 Frontmatter；
- 正文无需程序即可阅读。

### 13.4 关系和内容

- 所有新 ID、来源快照和图片引用都能解析；
- 闪念与永久认识的形成关系可追溯；
- 来源与松海自己的判断不混淆；
- 长篇论证、实际边界和演化内容不因模板转换被压缩丢失；
- 纯机器连接导航不进入新系统；
- 有意思对象不会被强制冒充来源、闪念或永久认识。

### 13.5 验证方式

- Markdown Frontmatter 解析检查；
- 中文状态白名单检查；
- 文件名正则检查；
- ID 唯一性与引用完整性检查；
- 来源快照和资产哈希检查；
- 迁移前后逐对象映射核对；
- `git diff --check`；
- 独立提交前复核。

## 十四、执行边界

本方案落盘不等于已经修改对象契约或执行迁移。正式实施需要按以下顺序：

1. 松海审阅本方案；
2. 修改并批准权威规则；
3. 生成迁移清单；
4. 松海裁决少量歧义项；
5. 分批迁移和验证；
6. 分批提交，默认不推送。
