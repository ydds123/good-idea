## 二、产品要解决的两个认知问题

Good Idea 不追求保存更多内容，也不让 AI 替松海完成判断。它只围绕两个容易被混在一起、但所需干预完全不同的问题组织能力。

### 1. 认识正在发生时，怎样不让现场消失或失真

此时最重要的是连续表达。过早要求标题、分类、结论和去向，会把注意力从正在形成的认识转移到系统管理上。

因此设置 `goodidea-capture`：它承担现场保护和最小干预，让表达先完整发生。整理候选只是现场结束后可能出现的结果，不是捕捉成功的必要条件。

### 2. 已有内容重新进入视野时，怎样判断是否值得继续投入

此时最重要的不是继续保存，而是作出价值判断：它是否值得继续占用注意力，缺口在哪里，最终应当如何处理。

因此设置 `goodidea-distill`：它承担重新进入、辨析和发展。形成永久卡片只是可能结果之一，不是预设终点。

## 三、为什么是两个 Skill

拆分依据是**认知状态和判断任务**，不是文件类型：

| 认知状态 | 首要风险 | Skill 的责任 |
|---|---|---|
| 想法仍在生成 | 被打断、被过早总结、被系统问题带偏 | 保护表达现场 |
| 内容已经存在并等待判断 | 用润色代替价值判断、默认把所有内容都加工成结论 | 帮助辨析和发展 |

两种任务对 Agent 的行为要求相反：前者应降低干预，后者才允许围绕真实缺口主动追问。放在同一个 Skill 中，会让“保存”和“裁决”相互污染。

## 四、人机协作的设计取向

### 松海保留判断权

Agent 可以复述、区分、比较、提出反例、召回历史或引入外部材料，但候选是否代表松海、对象是否正式成立，仍由松海裁决。现行作者权边界见 [`../规则/系统宪法.md`](../规则/系统宪法.md)。

### 现场、候选和正式对象分开

三者承担不同责任：现场保留实际发生的表达；候选暴露 Agent 的组织和推导；正式对象保存松海已经认领的内容。它们的准确身份和正式入口见 [`../规则/内容对象.md`](../规则/内容对象.md)。

### 先回应思考，再处理系统动作

链接解析、历史检索、整理和写入都只是支撑。它们不能抢占松海正在表达的问题。具体执行顺序见 [`../规则/协作协议.md`](../规则/协作协议.md)。

### 允许零产出

捕捉没有形成卡片、辨析后不再发展，仍可能是有效结果。系统的价值在于保护或改善真实判断，而不是提高对象数量。

## 五、为什么其他能力不继续拆 Skill

行动、有意思、外部来源和上下文召回都有明确的直接协议，但它们目前不需要独立的长程认知编排：

- 行动处理的是已经作出的现实承诺；
- 有意思处理的是暂时保留注意力入口；
- 外部来源处理的是材料本身；
- 上下文召回为当前任务提供背景。

它们可以被两个核心 Skill 调用，也可以直接执行。是否增加新的 Skill，取决于真实使用中是否出现稳定且独立的触发、上下文和停止条件，而不是取决于是否存在一种文件类型。

当前路由以 [`../AGENTS.md`](../AGENTS.md) 和两个 Skill 的 description 为准。

## 六、轻量实现取向

两个 Skill 只负责：

1. 识别当前意图；
2. 加载对应权威规则；
3. 组织对话顺序；
4. 在正确位置停止或交接。

它们不复制对象契约，也不预设 Kernel、应用、索引或复杂检索技术。这样做使认知规则可以独立于具体界面和实现演化。

## 七、如何判断这个设计是否成立

不在本文维护验收清单。实际判断依赖两类证据：

- 路由和边界是否符合 [`../验证/Skill路由验收.md`](../验证/Skill路由验收.md) 与 [`../验证/场景推演.md`](../验证/场景推演.md)；
- 真实使用中是否出现打断、误认领、对象冒充、过度召回或不必要流程，按 [`../验证/试运行协议.md`](../验证/试运行协议.md) 留下证据。

若证据要求改变对象语义、协作顺序或默认取舍，应修改各自的规则归属文件；只有“双 Skill 的认知任务划分为何成立”发生变化时，才修改本文。
